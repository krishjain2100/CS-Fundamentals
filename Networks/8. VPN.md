### Virtual Private Networks (VPN)

The term has three parts: **Virtual**, **Private**, and **Network**.

**Network**: A set of hosts, servers, and printers connected by a switch, with a router connecting the network to the outside.

**Private Network**: A network that is **not accessible from outside its physical boundary**. The router at the boundary blocks outside traffic, so only devices inside can reach the internal hosts.

**The Problem**: An organization with two sites in different cities (e.g.: Delhi and Sonepat ) has two separate private networks. Each is reachable only from within its own physical boundary, so hosts at one site cannot reach hosts at the other.

- **Solution 1: Leased Lines**: A dedicated physical line between the two sites' routers. The connection is private, but it has a **high cost**.

- **Solution 2: Use the Public Internet**: Instead, the public Internet can connect the private networks. This is a **VPN**, built with **tunnelling**:

	- **Virtual:** There is no physical link. The "link" is a logical tunnel over the shared Internet.
	- **Private:** Only the two endpoints can read or modify what goes through the tunnel.

**Properties Required:** Confidentiality, Integrity, Authentication

The tunnel crosses networks controlled by third parties (Trudy in the threat model), so it must provide the three goals from Network Security: packets are **encrypted** (confidentiality), carry a **MAC or signature** (integrity), and the endpoints are **authenticated** to each other. IPsec is the network-layer protocol that does this.

**Encapsulation**

The original packet (inner header + payload) is encrypted and authenticated, and placed as the payload of a new packet whose **outer header** is addressed to the tunnel endpoint (the VPN gateway). The gateway removes the outer header, verifies and decrypts the packet, and forwards the inner packet into the private network.

### Types of VPNs

| **Type**          | **Connects**                             | **Typical use**                                       |
| :---------------- | :--------------------------------------- | :---------------------------------------------------- |
| **Site-to-Site**  | Network to network                       | Linking an organization's sites                       |
| **Remote Access** | Network to an end client (an individual) | A user outside the organization accessing its network |


---
#### Site-to-Site VPN

- A **gateway router** sits at the edge of each site, and a tunnel is set up between the gateways across the Internet.
- Hosts inside a site run no VPN software and are unaware of the tunnel. The gateway encapsulates traffic leaving the site and decapsulates traffic entering it.
- **Linking the sites** means making the separate private networks reachable from each other, so a host at one site can talk to a host at another using private addresses.

**Example**

Two sites of one organization: Delhi (`10.1.0.0/16`, host `10.1.0.5`) and Sonepat (`10.2.0.0/16`, file server `10.2.0.9`). Host `10.1.0.5` sends a packet to `10.2.0.9`.

- **Without a VPN:** Source `10.1.0.5` and destination `10.2.0.9` are private addresses, so Internet routers do not route the packet and it is dropped.
- **With a site-to-site VPN:**
    1. The host sends the packet as usual and does nothing special.
    2. The Delhi gateway sees that `10.2.0.9` belongs to the Sonepat site. It encrypts the whole packet and wraps it in a new packet addressed to the Sonepat gateway's **public** IP.
    3. The new packet crosses the Internet normally, since its outer addresses are public.
    4. The Sonepat gateway verifies and decrypts it, removes the outer header, and delivers the original packet to `10.2.0.9`.
    5. The reply returns the same way.


**Multiple Sites**

- Each tunnel connects exactly two gateways, with its own authentication and session keys. For two sites to reach each other directly, they need a tunnel between them.
- In a full mesh of $n$ sites, each site has a tunnel to the other $n-1$ sites, giving $n(n-1)$ tunnel endpoints. Each tunnel has two endpoints, so the number of tunnels is $\frac{n(n-1)}{2}$, i.e., the number of pairs of sites.
- Each tunnel is set up independently: the two gateways authenticate each other and agree on keys for that tunnel only. Adding a site means setting up a new tunnel to every existing site.

#### Remote Access VPN

A user outside the organization (a laptop) connects to the organization's VPN gateway. The laptop has two addresses:

- A **public IP** `C_IP`, given by its local network, used to reach the Internet.
- A **private IP** `IP_A`, assigned by the VPN, from the organization's private address space. It is **not publicly routable**.

Notation: `R_IP` is the gateway's public IP and `IP_B` is the private IP of an internal host. 

| **Packet**               | **Inner header**       | **Outer header**       |
| :----------------------- | :--------------------- | :--------------------- |
| Client to internal host  | src `IP_A`, dst `IP_B` | src `C_IP`, dst `R_IP` |
| Reply from internal host | src `IP_B`, dst `IP_A` | src `R_IP`, dst `C_IP` |

**Remote Access Modes**

The two modes differ in **where on the device the traffic is captured and sent into the VPN**: at the network layer for the whole device (tunnel mode), or at the application layer for individual applications (application mode). 

|                                               | **Tunnel Mode**                                                                                                                                           | **Application Mode**                                                                                                                                                                                |
| :-------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Layer**                                     | Network layer (IP packets)                                                                                                                                | Application layer (an application's connection)                                                                                                                                                     |
| **Mechanism**                                 | A **virtual interface** (TUN, e.g., `tun0`) is created and the **routing table** sends packets into it. The VPN client encapsulates **whole IP packets**. | The **application itself** (or a per-application proxy) opens an encrypted connection to the VPN server and sends its own data through it. No virtual interface and no change to the routing table. |
| **What is covered**                           | **All traffic of the device**, from every application, including ones unaware of the VPN                                                                  | **Only the selected application(s)**. All other applications connect directly.                                                                                                                      |
| **Applications must support it**              | No, it is transparent                                                                                                                                     | Yes, or must be configured to use the VPN (e.g., a browser configured with a proxy)                                                                                                                 |
| **Privileges**                                | Needs OS-level privileges to create the interface and change routes                                                                                       | Runs as an ordinary user process                                                                                                                                                                    |
| **Gets an IP address in the private network** | Yes (`IP_A`), so any protocol works                                                                                                                       | Not necessarily, only the application's connections are relayed                                                                                                                                     |
| **Typical form**                              | Commercial VPN apps, IPsec, OpenVPN, WireGuard clients                                                                                                    | Browser-based "web VPN" portals, SOCKS/HTTPS proxies, SSH port forwarding, per-app VPN                                                                                                              |

### Tunnel Mode

This is the mechanism described in How a VPN Works on the Endpoint: with the default route pointing to `tun0`, every outgoing IP packet is delivered to the VPN client, which encrypts the **entire packet** (inner header included), prepends a new outer header addressed to the VPN server, and sends it out of the physical interface. Because the routing table decides what goes into the tunnel, tunnel mode can also be **partial** (**split tunnelling**): only the organization's prefixes are routed to `tun0` and everything else goes out directly, as the `10.0.0.0/24` row in the example table does.

---
### Application Mode

The VPN is part of the application's own data path. The application connects to the VPN server (typically over TLS) and asks it to relay its connections to the private network or to the destination. The OS is unaware of the VPN, so the routing table is unchanged.

- **Advantages:** No privileges and no OS-level changes. Only the traffic that needs protection pays the VPN overhead.
- **Disadvantages:** Traffic from every application that is not configured goes out unprotected, including its DNS queries. This can reveal metadata the VPN was meant to hide. Each application needs its own support or configuration.

---
### Individual VPNs (Commercial VPN Services)

Here there is no private network behind the gateway, only a **VPN server** in front of the open Internet.

- The user connects to the VPN server through the tunnel.
- Traffic to a destination (e.g., `fb.com`) goes through the tunnel to the VPN server, which forwards it with **its own IP** (`S_IP`) as the source.
- The destination sees `S_IP` and not the user's IP.

---
### Use Case: Hiding Network Metadata

**Network metadata** is information about who talks to whom: destination IPs, and the domain names visible in DNS queries and connection setup. Even when the content is encrypted (TLS), this metadata is visible to **network intermediaries** such as the ISP. It reveals the user's browsing activity and is used for surveillance/tracking and behavioural profiling. What metadata reveals:

| **Site visited**                                  | **Inference**                          |
| :------------------------------------------------ | :------------------------------------- |
| `thyroid-support.org`                             | Possible health condition              |
| `scholarship-finder.org`, `university.edu/grants` | Financial concerns, academic interests |

**How a VPN Hides It**

Example: the user has IP `1.2.3.4`, the VPN server has IP `5.6.7.8`, and the destination is GitHub. Passive network observers can sit on either side of the VPN server:

| **Observer position** | **Sees** | **Does not see** |
| :--- | :--- | :--- |
| Between the user and the VPN server | `1.2.3.4` $\leftrightarrow$ `5.6.7.8`: the user uses a VPN server | The destination |
| Between the VPN server and GitHub | `5.6.7.8` $\leftrightarrow$ GitHub's IP (the destination is likely `github.com`) | That the user is `1.2.3.4` |
Only the VPN server knows both the user and the destination.

### How a VPN Works on the Endpoint

A VPN client on a device uses a **tunnel interface**, a virtual network interface (TUN, e.g., `tun0`), alongside the physical interface (e.g., `wlan0`).

1. The VPN client creates the virtual interface `tun0`.
2. The OS routing table sends packets (**all packets**, in tunnel mode) to `tun0`.
3. The VPN client application reads these packets from `tun0`, encrypts and encapsulates them, and sends them as ordinary packets with the **destination set to the VPN server's IP**, out through the physical interface `wlan0` to the Internet.

**Routing Table on the Client**

| **Destination** | **Interface** | **Metric** |
| :--- | :--- | :--- |
| `0.0.0.0` (default) | `tun0` | 2 |
| `10.0.0.0/24` | `wlan0` | 10 |
| `192.168.0.0/16` (partly illegible on the slide) | `wlan0` | 5 |
| `0.0.0.0` (default) | `wlan0` | 3 |
| VPN server IP | `wlan0` | 1 |

The router picks the **longest matching prefix**, and among equal prefixes the entry with the **lowest metric**:

| **Destination** | **Route chosen** | **Why** |
| :--- | :--- | :--- |
| VPN server IP | `wlan0` | The most specific route (a single address). Without it, the encrypted packets would match the default route, go back into `tun0`, and loop. |
| `10.0.0.5` | `wlan0` | The `/24` is more specific than the default routes, so local traffic bypasses the tunnel |
| Any other address (e.g., `8.8.8.8`) | `tun0` | Only the two default routes match, and `tun0` has the lower metric (2 < 3) |

### VPN Proliferation and Trust

- VPN adoption has skyrocketed and it is now a multi-billion-dollar industry (projected to reach 137 billion USD by 2030, Business Wire).
- From the user's perspective, a VPN is a **transfer of trust**: the user no longer has to trust the local network and the ISP, but must now trust the VPN provider, which sees the same traffic and metadata.

**Question:** Are VPNs upholding security and privacy standards?

### MVPNalyzer: Auditing Mobile VPNs

**MVPNalyzer** is a framework for auditing the security and privacy of mobile (Android) VPN apps, published at NDSS 2026 and presented in the lecture as the lecturer's own work ("we built MVPNalyzer").

**Key Questions**

| **#** | **Question** | **Analysis module** |
| :--- | :--- | :--- |
| 1 | Does the VPN transmit **cleartext traffic** (e.g., HTTP)? | Unencrypted Traffic |
| 2 | Does the VPN **leak which websites** the user is visiting? | Traffic Leak |
| 3 | Does the VPN make an effort to **obfuscate itself** from network adversaries? | VPN Obfuscation |
| 4 | Does the VPN engage in **user tracking or device fingerprinting**? | Tracking & Fingerprinting |
| 5 | Does the VPN **properly configure its tunnel protocol**? | VPN Configuration |

**System Architecture**

| **Stage** | **Components** |
| :--- | :--- |
| **Data Collection** (on the Android device) | Instrumentation and tunnel connection. Raw data: **socket statistics**, **WLAN pcap**, **TUN pcap**, the **SSLKEYLOG** file (TLS session keys) and the app's storage |
| **Data Processing** (on a laptop) | **Traffic attribution** (which app produced which traffic), **TLS decryption** using the SSLKEYLOG, producing processed pcaps and the extracted VPN configuration |
| **Analysis** | The five modules above |

The WLAN pcap shows what the network actually sees, and the TUN pcap shows what the apps send into the tunnel. Comparing the two is how traffic that bypasses the tunnel or leaves unencrypted can be found (my inference from the interface description above, the slide only lists the captures).

**Findings**

- A study of **281 free Android VPN apps**, which together have **2.4 billion installs**, found traffic leaks, unencrypted data, and tracking (headline from The Hacker News).
- The overview plot counts apps by each combination of the five audited categories (Unencrypted, Leak, Obfuscation, Tracking, OVPN Config, the OpenVPN configuration check).
- Google's Android App Safety team contacted the authors for package names, download dates, store, and sha256 hashes in order to examine the same apps and versions.
