Unlike the transport and application layers, there is a piece of the network layer in each and every host and router in the network. Note that the routers have no upper layers above the network layer because routers do not run application and transport-layer protocols.

### Forwarding vs. Routing

| **Feature**        | **Data Plane (Forwarding)**                                          | **Control Plane (Routing)**                                                   |
| ------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **Scope**          | Router-local (navigating a single interchange)                       | Network-wide (planning the entire end-to-end trip)                            |
| **Primary Action** | Moves arriving packets from an input link to the correct output link | Determines the overarching path packets take from sender to receiver          |
| **Timescale**      | Nanoseconds (implemented in hardware)                                | Seconds (implemented in software)                                             |
| **Mechanism**      | Reads packet headers and executes a **Forwarding Table** lookup      | Executes **Routing Algorithms** to compute and populate the Forwarding Tables |

### The Control Plane: Two Architectures

The way a router gets its Forwarding Table defines the network's architecture. 

- **The Traditional Approach:** Every single router contains both data-plane hardware and control-plane software. The routing algorithm runs inside the router itself, constantly talking to neighbouring routers via routing protocols (like OSPF or BGP) to collaboratively calculate the Forwarding Table.

![[Screenshot 2026-09-27 at 10.12.26 PM.png]]

- **The SDN Approach (Software-Defined Networking):** The control plane is physically separated from the router. A remote, centralised server (the SDN Controller) computes the end-to-end paths for the entire network and pushes the resulting Forwarding Tables down to the routers. The routers exist solely to execute data-plane forwarding.

![[Screenshot 2026-09-27 at 10.12.08 PM.png]]

An unrealistic, but technically feasible solution is maintenance by human network operators physically present at the routers. In this case, no routing protocols would be required. Operators would need to communicate to ensure that the forwarding tables were configured correctly. It’s likely that this would be more error-prone and much slower to respond to changes in the network topology than a routing protocol. 

---
### The Internet Service Model

A network's service model dictates what guarantees it makes to the transport layer (TCP/UDP) regarding packet delivery. While other architectures (like ATM network architecture) guarantee in-order delivery, bounded delay, and guaranteed minimal bandwidth, the Internet makes **zero guarantees**. Packets might be lost, delivered out of order, indefinitely delayed, or throttled. Internet just provides a **Best-Effort Service**. A network that delivered no packets to the destination would satisfy the definition of best-effort delivery service

There have also been proposed service model extensions to the Internet architecture, for example, the **Intserv architecture** which aims to provide end-to-end delay guarantees and congestion-free communication. Interestingly, in spite of these well-developed alternatives, the Internet’s basic best-effort service model combined with adequate bandwidth provisioning and bandwidth-adaptive application-level protocols such as the DASH protocol we encountered in Section 2.6.2 have been good enough to enable an amazing range of applications

### Hardware vs. Software

- **Data Plane is implemented in Hardware (Nanoseconds):** If an input port is receiving a 100 Gbps stream of 64-byte IP datagrams, it has exactly 5.12 nanoseconds to process each packet. If N ports are combined on a line card (as is often done in practice), the datagram-processing pipeline must operate N times faster, far too fast for software implementation. Forwarding hardware can be implemented either using a router vendor’s own hardware designs, or constructed using purchased merchant-silicon chips (for example, as sold by companies such as Intel and Broadcom). 

- **Control Plane is implemented in Software (Milliseconds/Seconds):** Calculating network paths is complex but doesn't happen per-packet. The Routing Processor runs standard  software on a normal CPU to handle a router’s control functions, executing the routing protocols or communicating with the remote controller (in the SDN case) and performing management functions.

### Forwarding Types

When the Input Port does its lookup, it uses one of two paradigms:

- **Destination-Based Forwarding:** The router determines the output port by looking exclusively at the packet's final Destination IP Address.

- **Generalized Forwarding:** The router determines the output port, or executes other actions, based on a combination of multiple packet header fields (e.g., Source IP, TCP/UDP ports, Protocol). This allows the network device to route traffic differently based on its origin, prioritise specific packets, or block them entirely (acting as a firewall).

### Input Port Processing

- **Network Layer:** Consults the forwarding table to determine the correct output port and pushes the packet into the switching fabric. If the switching fabric is currently in use, the packet is temporarily queued at the input port.

- **Auxiliary Actions:**
    - Checks the packet's version number, checksum, and Time-To-Live (TTL) fields.
    - Rewrites the TTL field and the checksum.
    - Updates network management counters (e.g., number of IP datagrams received).

---
### Forwarding Table Architecture

- **Decentralised Execution:** The centralised routing processor (or remote SDN controller) calculates the forwarding table and pushes a shadow copy to each input line card over a separate internal bus (e.g., a PCI bus). Each line card gets the same single copy and each input chip on the line card uses this single copy.

- **Bottleneck Avoidance:** Maintaining copies allows input ports to make local forwarding decisions simultaneously without invoking the routing processor on a per-packet basis.

---
### Destination-Based Forwarding Mechanics

- **Prefix Matching:** Because 32-bit IP addresses yield over 4 billion possible combinations, brute-force exact-match tables are impossible. Routers instead group address ranges into prefixes. The router matches the prefix of an incoming packet's destination address against the table entries.

- **Longest Prefix Matching Rule:** If a single destination address matches multiple prefix entries in the table, the router forwards the packet to the link interface associated with the longest matching prefix.

- **Hardware Acceleration:** At Gigabit transmission rates, lookups must execute in nanoseconds. This requires hardware implementation using embedded on-chip DRAM and fast SRAM (acting as a DRAM cache).

- **Ternary Content Addressable Memories (TCAMs):** Specialized hardware that retrieves the correct forwarding table entry in constant time. Enterprise routers can hold upwards of a million TCAM entries. 

- Once a packet’s output port has been determined via the lookup, the packet can be sent into the switching fabric.

### Switching Fabrics

The switching fabric forwards packets from an input port to an output port.

**Switching via Memory**

- **Legacy Architecture:** Operated under direct CPU (routing processor) control. An input port triggered an interrupt, copied the packet into processor memory, and the CPU extracted the destination, performed the lookup, and copied the packet to the output buffer.

- **Bandwidth Constraint:** If memory bandwidth allows a maximum of B packets per second to be written/read, total forwarding throughput is strictly limited to less than B/2. Shared system buses prevent simultaneous packet forwarding.

- **Modern Execution:** Input line cards independently perform lookups and write packets directly into the appropriate output port's portion of a large global shared memory, resembling shared-memory multiprocessors (e.g., Cisco Catalyst 8500).


**Switching via a Bus**

- **Mechanism:** The input port prepends a switch-internal label indicating the target output port and broadcasts the packet across a shared bus, entirely bypassing the routing processor. All output ports receive the broadcast, but only the matching port captures the packet and strips the temporary label.

- **Bandwidth Constraint:** Strictly sequential. Switching speed is completely bottlenecked by the single bus speed. Simultaneous packet arrivals at different input ports force all but one packet to wait in queue.

- **Use Case:** Sufficient for small local area and enterprise networks.


**Switching via an Interconnection Network**

- **Crossbar Switch Mechanism:** A grid of 2N buses connecting N input ports to N output ports. A dedicated switch fabric controller (whose logic is part of the switching fabric itself) dynamically opens and closes intersections (cross-points) between vertical and horizontal buses. The intersection between A and Y is closed when input is from port A and output is to port Y.

- **Parallelism (Non-Blocking):** Capable of forwarding multiple packets simultaneously, provided they target _different_ output ports. If multiple packets target the exact same output port, only one transmits while the others queue at the input port.


![[Screenshot 2026-09-28 at 12.09.23 AM.png]]

**Advanced Interconnection Scaling**

- **Multi-Stage Switching:** Employs multiple stages of switching elements to allow packets from different input ports to proceed toward the exact same output port simultaneously. For same output case, there can be a queue at the output port if it cannot take multiple packets simultaneously.

![[Screenshot 2026-09-28 at 1.56.47 AM.png]]

- **Parallel Fabrics (Chunk Spraying):** Routers scale capacity by running $N$ switching fabrics in parallel. The input port fragments a packet into $K$ smaller chunks, transmits them simultaneously across $K$ fabrics, and the output port reassembles the original packet.

### Queuing Dynamics in Routers

- **Determinants:** The location and severity of queuing depend entirely on traffic load, line transmission speed ($R_{line}$), and the switching fabric transfer rate ($R_{switch}$).

- **Packet Loss:** Occurs strictly when queues grow large enough to exhaust a port's available memory.

---
#### Input Queuing

Occurs when $R_{switch}$ is not sufficient to handle $R_{line}$. Consider a crossbar switching fabric and suppose that:
- All link speeds are identical
- One packet can be transferred from any one input port to a given output port in the same amount of time it takes for a packet to be received on an input link.
- Packets are moved from an input queue to their desired output queue in an FCFS manner. 
- Multiple packets can be transferred in parallel, as long as their output ports are different.
- However, if two packets at the front of two input queues are destined for the same output queue, then one of the packets will be blocked and must wait at the input queue a the switching fabric can transfer only one packet to a given output port at a time.

**Head-of-the-Line (HOL) Blocking:** A queued packet must wait for transfer (even if its target output port is completely free) because it is trapped behind another packet at the front of the queue that is blocked by output port contention. Due to HOL blocking, input queues grow to unbounded lengths (causing massive packet loss).

![[Screenshot 2026-09-28 at 2.11.08 AM.png]]

Light shaded packet at Input 3 must wait if Dark shaded packet at Input 1 is selected first.

----
#### Solutions to HOL

**Virtual Output Queuing (VOQ)**

- Replaces the single FIFO queue at each input port with $N$ separate logical queues (one dedicated to each of the $N$ output ports).
- If a packet destined for Output X is physically blocked by contention, the scheduler simply bypasses it and transmits a packet from a different VOQ at that same input port destined for a currently available output port.
- Completely eliminates Head-of-the-Line blocking.

**Switch Fabric Speedup**

- Increases the internal switching fabric speed to be $N$ times faster than the input line speed ($R_{switch} = N \cdot R_{line}$).
- Clears all packets immediately upon arrival, physically preventing input queues from forming.
- Shifts the buffering burden and queuing delay entirely to the output ports.

**Combined Input-Output Queuing (CIOQ) with Centralised Scheduling**

- A moderate fabric speedup (e.g., 2x) combined with VOQs to balance hardware costs.
- Requires a centralised bipartite matching algorithm (such as the **iSLIP** algorithm detailed in McKeown's 1997 paper) to iteratively pair non-conflicting input and output ports to maximize throughput during each clock cycle.

---
#### Output Queuing

- **Trigger:** Occurs even if $R_{switch}$ is $N$ times faster than $R_{line}$. If $N$ input ports simultaneously forward packets to the exact same output port, the output port can only transmit one packet per time unit onto the link, forcing the remaining $N-1$ packets to queue.

- **Buffer Exhaustion Policies:**
    - **Drop-Tail:** Immediately drops the newly arriving packet.
    - **Eviction:** Removes one or more already-queued packets to accommodate the new arrival. In some cases, it may be advantageous to drop (or mark the header of) a packet before the buffer is full in order to provide a congestion signal to the sender. This marking could be done using the Explicit Congestion Notification bits discussed earlier.

- **Active Queue Management (AQM):** Algorithms that proactively drop or mark packets (e.g., using Explicit Congestion Notification bits) _before_ the buffer fills to signal incipient congestion to the TCP sender. Examples: **Random Early Detection (RED), PIE (Proportional Integral controller Enhanced), and CoDel.**

- **Scheduling:** Requires a packet scheduler at the output port to select which queued packet is transmitted next.

---
### Buffer Sizing Architecture

The $RTT$ in the following formulae is the average Round-Trip Time of all the active TCP flows passing through that specific link. A larger $RTT$ means the TCP sender has a much slower reaction time. The router needs a proportionally larger buffer to absorb all the data the sender blindly fires into the network before it finally receives an ACK and adjusts its speed.

| **Environment**                          | **Calculation Formula**             | **Context**                                                                                               |
| ---------------------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Legacy / Edge (Small TCP Flow Count)** | $B = RTT \times C$                  | Total buffer size ($B$) equals the average Round-Trip Time ($RTT$) multiplied by the link capacity ($C$). |
| **Modern Core (Large TCP Flow Count)**   | $B = \frac{RTT \times C}{\sqrt{N}}$ | Used when a large number of independent TCP flows ($N$) share a backbone link.                            |

**Reasons for Modern Core Router Formula:**

- As the number of independent TCP flows ($N$) scales to the thousands, synchronized bursting becomes statistically impossible. The transmission peaks of some flows perfectly fill the valleys of others, smoothing the aggregate traffic rate.
- Because bandwidth is heavily divided, no individual flow's peak variance is large enough to overwhelm the link capacity.
- Extreme traffic spikes are eliminated, allowing the required physical memory to shrink proportionally by a factor of $\frac{1}{\sqrt{N}}$.

---
### Over-Buffering

While large buffers successfully absorb short-term statistical fluctuations (lowering packet loss), excessive buffer sizing introduces two failure modes:

1. **End-to-End Delay:** A massive buffer means a longer physical queue. Packets spend tens to hundreds of milliseconds trapped in memory waiting for transmission, destroying real-time interactive applications (gaming, VoIP, teleconferencing).

2. **Transport-Level Failure:** TCP relies on Round-Trip Time ($RTT$) as its primary feedback mechanism. Because large buffers trap packets instead of dropping them, the $RTT$ artificially inflates. This lag blinds the TCP sender, making its congestion-control algorithms slow to react to actual network congestion.

---
### Edge Buffer-bloat

The network edge (e.g., home routers) lacks the statistical multiplexing benefits of the core. A single bursty flow can permanently degrade latency. Consider:

A home router link takes 20 ms to transmit a packet. The network RTT is 200 ms. At $t=0$, an initial burst of 25 TCP packets arrives in the queue. In the 200 ms it takes for the first ACK to return, the router processes exactly 10 packets ($200\text{ ms} / 20\text{ ms/packet}$).

**At $t=200$ ms:** The first ACK arrives. The router has transmitted 10 packets and is beginning the 11th. Exactly **15 packets** remain trapped in hardware queue. TCP is ACK-clocked, it sends one new packet every time it receives an ACK. Because the router transmits one packet every 20 ms, an ACK returns to the sender every 20 ms. The sender pushes a new packet into the queue at the exact same rate the router pulls one out.

As a result, the queue locks into an equilibrium, maintaining a permanent, standing length of 15 packets. The pipe operates at maximum throughput, but every subsequent packet suffers a mandatory, permanent queuing delay of 300 ms ($15 \text{ packets} \times 20 \text{ ms}$), destroying real-time application performance.

**Solution:** Because this persistent delay occurs even with zero competing traffic, modern edge standards (like DOCSIS 3.1) mandate **Active Queue Management (AQM)**. AQM intentionally drops packets proactively, signalling TCP to throttle its sending rate and breaking the standing queue without sacrificing bulk throughput.

### Packet Scheduling Architecture

The outgoing link scheduler dictates the exact transmission order of packets waiting in the hardware queue.

**1. First-In-First-Out (FIFO)**

- Single queue. Packets are transmitted strictly in their order of arrival.
- If arrival rate exceeds transmission rate, the queue fills. A packet-discarding policy dictates whether the newly arriving packet or an existing queued packet is dropped.

**2. Priority Queuing**

-  Multiple distinct queues based on traffic classification (e.g., priority TCP/UDP ports, or real-time VoIP packets might receive priority over e-mail packets).
- The scheduler transmits from the highest-priority queue that contains packets. Lower-priority queues are only served if all higher-priority queues are entirely empty. Packets within the exact same priority class are served via FIFO.
- **Non-Preemptive Execution:** Once a packet begins hardware transmission over the link, it cannot be interrupted, even if a higher-priority packet arrives mid-transmission.

**3. Round Robin**

- Multiple distinct queues based on classification. No strict priority hierarchy. The scheduler polls queues in a strict circular sequence (Class 1 $\rightarrow$ Class 2 $\rightarrow$ Class 1).
- **Work-Conserving Property:** The link is never left idle if _any_ packet is queued. If the scheduler polls an empty queue, it does not wait. It immediately skips to check the next queue in the sequence.

**4. Weighted Fair Queuing (WFQ)**

- A generalized, weighted extension of Round Robin. Each queue (class $i$) is assigned a specific numerical weight ($w_i$). The scheduler serves queues circularly but allocates bandwidth proportionally based on these weights.
- **Throughput Guarantee:** WFQ is work-conserving. During any interval where class $i$ has packets to send, it is mathematically guaranteed a minimum fraction of the total link bandwidth ($R$). Minimum guaranteed throughput = $R \times \frac{w_i}{\sum w_j}$, where the denominator ($\sum w_j$) is the sum of the weights of only the queues that currently possess waiting packets.
- In physical hardware, packets are discrete. Once a packet begins transmission, it cannot be interrupted (***DID NOT UNDERSTAND WHY IT CANNOT BE INTERRUPTED***). Therefore, WFQ routers can only approximate this throughput guarantee.

### Net Neutrality

Packet scheduling mechanisms provide the technical capability for ISPs to enforce differential service levels by classifying traffic based on IP datagram headers (e.g., port numbers or source IP addresses).

**Net Neutrality Principles**

The 2015 US FCC Order (rolled back in 2017, replaced with a policy centered on ISP transparency and disclosure) established three core prohibitions:

- **No Blocking:** Forbids dropping packets destined for lawful content or non-harmful devices.

- **No Throttling:** Forbids artificial degradation (via queue manipulation) of specific lawful traffic classes on the basis of Internet content, application, or service.

- **No Paid Prioritisation:** Forbids using WFQ or strict priority queues to favor specific traffic in exchange for financial compensation.

**Historical Technical Violations**

- **Competitive Blocking (2005):** A North Carolina ISP blocked VoIP traffic (Vonage) at the network level to protect its own competing legacy telephone service.

- **Active Interference / Connection Hijacking (2007):** Comcast degraded BitTorrent traffic not just via passive queue throttling, but by internally fabricating and injecting forged **TCP RST (Reset)** packets into the network to actively force end-hosts to tear down their P2P connections.

**Economic Debate**

-  **Argument Against Strict Neutrality:**

	- Treating all packets equally prevents the creation of guaranteed low-latency network slices required for next-gen applications (e.g., autonomous vehicles, remote surgery).
	
	- Charging massive content providers for paid prioritization generates the billions in capital required to lay new fiber and improve network for all.

- **Argument For Strict Neutrality:**
	
	- Allowing paid prioritisation incentivises ISPs to artificially degrade standard traffic to force companies to pay for the premium lane.
	
	- If reliable network performance requires capital, new startups cannot compete with incumbent tech giants who can afford the tolls, ultimately crushing market competition.

### IPv4 Datagram

![[Screenshot 2026-09-30 at 1.17.19 PM.png]]

**Header Fields & Their Functions:**

- **Version (4 bits):** Identifies the IP version (IPv4). Using this, the router determines how to interpret the remainder of the IP datagram.

- **Header Length (4 bits):** This field is mandatory because the `Options` field makes the IPv4 header variable in size. Most IP datagrams do not contain options, so the typical IP datagram has a 20-byte header.

- **Type of Service (TOS) / Differentiated Services:** Bits used by the router's packet scheduler (like WFQ) to identify priority traffic classes (e.g., VoIP vs. FTP). Two of the TOS bits are used for Explicit Congestion Notification.

- **Datagram Length (16 bits):** The total packet size (header + data). The maximum is 65,535 bytes, but in practice, packets are almost always kept under 1,500 bytes to physically fit inside a standard Ethernet frame payload without fragmenting. The standard Ethernet hardware enforces a MTU of 1,500 bytes for its payload section.

- **Identifier, Flags, Fragmentation Offset:** Used to track and reassemble IP datagrams that had to be broken into smaller chunks to cross a link with a small MTU. (Note: Hardware fragmentation is so resource-intensive that IPv6 abolishes this feature entirely).

![[Screenshot 2026-10-26 at 12.57.18 PM.png]]

The `fragflag` is set to `0` in the last fragment to signal to the destination host that this is the **final piece** of the original datagram. The `fragflag`  is located inside the **Flags** field.

The fragmentation offset is calculated by dividing the number of preceding data bytes by 8. The IPv4 offset field is designed to count in 8-byte blocks rather than individual bytes to save header space (allowing a 13-bit field to map a 65,535-byte maximum datagram). With a 1,500-byte MTU limit, the maximum application data each fragment can actually carry is 1,480 bytes (`1500 - 20 = 1480`).

- **Fragment 1:** Because zero data precedes it, the offset is `0 / 8 = 0`.
- **Fragment 2:** This carries the next block of data, starting exactly at byte 1,480. The router calculates the offset as `1480 / 8 = 185`.
- **Fragment 3:** This carries the remaining data, starting after two 1,480-byte payloads. The router calculates the final offset as `2960 / 8 = 370`.


- **Time-to-Live (TTL):** Routers decrement this value by 1 upon processing the datagram. If TTL hits 0, it immediately drops the packet.

- **Protocol:** Used only when an IP datagram reaches its final destination. It tells the destination host's OS which protocol stack to hand the payload to (e.g., `6` for TCP, `17` for UDP). The protocol number is the glue that binds the network and transport layers together, whereas the port number is the glue that binds the transport and application layers together.

- **Header Checksum:** It is computed by treating each 2 bytes in the header as a number and summing these numbers using 1s complement arithmetic.  A router computes the header checksum for each received IP datagram. Routers typically discard datagrams for which an error has been detected. Because every router decrements the TTL field, the header's bits changes at every single hop. So every router must recalculate and rewrite the checksum for every packet it processes before forwarding it.

- **Source & Destination IP Addresses (32 bits each):** Routing identifiers.

- **Options:** An expandable field for rare header additions. From a hardware perspective, this field is highly problematic: it forces the header to be variable-length, which prevents high-performance routers from processing packets in predictable, uniform clock cycles.

- **Data (Payload):** In most circumstances, it contains the transport-layer segment (TCP or UDP) to be delivered to the destination. However, the data field can carry other types of data, such as ICMP messages.

An IP datagram has a total of 20 bytes of header (assuming no options). If the datagram carries a TCP segment, then each datagram carries a total of 40 bytes of header (20 bytes of IP header plus 20 bytes of TCP header) along with the application-layer message.


**Q. Why does TCP/IP perform error checking at both the transport and network layers?**

- Note that only the IP header is checksummed at the IP layer, while the TCP/UDP checksum is computed over the entire TCP/UDP segment (including the data body). 

- TCP/UDP and IP do not necessarily both have to belong to the same protocol stack. TCP can, in principle, run over a different network-layer protocol (for example, ATM)  and IP can carry data that will not be passed to TCP/UDP.

**Q. What are some use-cases for `Options`:**

- **Record Route:** As the datagram travels to its destination, each router it passes through appends its own IP address into the Options field. This creates a complete breadcrumb trail of the exact physical path the packet took, which was historically useful for network mapping and troubleshooting.

- **Strict and Loose Source Routing:** Instead of allowing routers to independently determine the best path using their forwarding tables, the sender embeds a specific list of router IP addresses in the Options field. The network is forced to forward the packet exactly along that pre-dictated path.

- **Time-stamping:** Each router along the path inserts a timestamp into the Options field as it processes the packet, allowing network engineers to calculate precise hop-by-hop latency and queueing delays.

### IPv4 Addressing & Network Architecture

IP addresses are bound to **interfaces** (the physical boundary between a device and the network link), not to the host or router itself. Because a router's entire job is to bridge different links, every router inherently possesses multiple interfaces, and therefore multiple IP addresses.

A subnet is an isolated network island of interconnected interfaces that can communicate directly _without_ needing an intervening router (e.g., devices on the same Ethernet switch or Wi-Fi access point).

To identify all subnets in a network topology, mentally detach every interface from its host/router. Every resulting isolated physical segment. including the point-to-point links connecting two routers together, is a distinct subnet. Example: first image has 3 subnets, whereas second one has 6. The blank clouds could be Ethernet switch or Wi-Fi access point (discussed later).

![[Screenshot 2026-09-30 at 2.27.34 PM.png]]

![[Screenshot 2026-09-30 at 2.27.46 PM.png]] 
**Broadcast Addresses:**
- **Limited Broadcast (`255.255.255.255`):** A special destination IP used when a host wants to communicate with every other host on its immediate physical subnet, typically before it even knows its own IP or subnet mask (e.g., during DHCP Discovery, discussed below). Routers strictly block these and will never forward them outside the local link.
- **Directed Broadcast (e.g., `192.168.1.255`):** Calculated by setting all the host bits of a specific network prefix to `1`. Sending a packet here reaches every host on that specific target subnet. While these can theoretically be routed across the internet to target a remote subnet, modern routers block them by default to prevent security vulnerabilities

From the discussion above, it’s clear that an organisation (such as a company or academic institution) with multiple Ethernet segments and point-to-point links will have multiple subnets, with all of the devices on a given subnet having the same subnet address. In principle, the different subnets could have quite different subnet addresses. In practice, however, their subnet addresses often have much in common.

### CIDR (Classless Inter-domain Routing)

CIDR is the modern Internet's address assignment strategy, generalising the concept of subnetting into a flexible $a.b.c.d/x$ format.

- **Prefix ($x$):** The first $x$ bits represent the network portion of the address. This is the only part of the address that routers outside the organisation care about.

- **Internal Bits ($32-x$):** The remaining bits identify specific devices within the organisation. Network administrators can further divide these remaining bits to create additional internal subnets (e.g., taking an assigned `/21` block and carving it into multiple internal `/24` subnets).


**CIDR Calculation Example (`192.168.10.0/26`):** 

- **Subnet Mask:** `255.255.255.192` (The final octet `11000000` in binary equals `192`. Bits that are 1 belong to the network and rest belong to host ). 

- **Number of Addresses:** `64` ($2^6$ derived from the 6 remaining host bits).

- **Network Address:** `192.168.10.0` (The first address in the block, calculated by setting all host bits to `0`. It is reserved for routing tables to identify the subnet itself and cannot be assigned to a device). 

- **Broadcast Address:** `192.168.10.63` (The final address in the block, calculated by setting all host bits to `1`. Used to reach all hosts in this specific subnet). 

- **Usable Host Range:** `192.168.10.1` to `192.168.10.62` (The assignable addresses sandwiched between the network and broadcast addresses).


**CIDR allows for efficient hierarchical routing.

- An ISP can take a massive contiguous address block (e.g., a `/20`) and carve it into smaller chunks (e.g., eight `/23` blocks) for its enterprise clients. Instead of advertising all eight individual `/23` networks to the global Internet, the ISP only advertises its `/20` prefix. This compresses the size of global routing tables, as the outside world doesn't need to know the internal layout of the ISP's client networks.

**Longest Prefix Matching for Mobility**

If an organisation physically moves to a new ISP, renumbering every host and router in their building to match the new ISP's address block is incredibly costly. CIDR and routing algorithms provide a workaround:

- The organisation simply takes its original block (e.g., `/23`) to the new subsidiary ISP.
- The original ISP continues to advertise its massive `/20` block to the Internet.
- The _new_ ISP simultaneously advertises the organisation's specific `/23` block to the Internet.
- When a global router receives a packet destined for that organisation, it sees two valid paths (the `/20` and the `/23`). It automatically forwards the packet to the new ISP by applying the **Longest Prefix Matching** rule, as a 23-bit match is more specific than a 20-bit match.


**Classful Addressing (Legacy)**

Before CIDR, IP addressing was strictly constrained into rigid classes, which proved disastrous for scaling. Network prefixes were locked strictly to 8, 16, or 24 bits (known as Class A, B, and C networks). A Class C (`/24`) subnet only supported 254 hosts (two of the 2^8 = 256 addresses are reserved for special use), which was too small for many businesses. However, the next step up, a Class B (`/16`), supported 65,534 hosts, which was massively oversized.

### DHCP (Dynamic Host Configuration Protocol)

Manual IP configuration is unscalable for modern networks where devices constantly join and leave. DHCP is a client-server protocol that manages network configurations.

Beyond allocating an IP address (which can be assigned permanently or temporarily), a DHCP server dynamically provisions three other critical pieces of network data to the connecting host:

1. **Network Mask:** Indicating network versus host portion of address.
2. **Default Gateway:** The IP address of the first-hop router (gateway).
3. **Local DNS Server:** Name & IP address of DNS Server.

![[Screenshot 2026-10-26 at 12.08.23 PM.png]]

**The 4-Step Handshake (DORA)**

When a device connects to a subnet, it has no IP address and does not know the identity of the local DHCP server. Therefore, it must rely on UDP broadcast messages (`255.255.255.255`) to communicate (specifically ports 67 and 68).

- **1. Discover:** The arriving client broadcasts a `DHCPDISCOVER` message (using a source IP of `0.0.0.0`) to find an available server.

- **2. Offer:** The DHCP server responds with a `DHCPOFFER` containing a proposed IP address (`yiaddr`), network mask, and lease duration. (Note: The server must broadcast this offer back to `255.255.255.255` because the client still does not have an active IP address to receive a direct unicast message).

- **3. Request:** If multiple DHCP servers exist on the subnet, the client may receive multiple offers. It selects one and broadcasts a `DHCPREQUEST` to officially claim those specific parameters.

- **4. ACK:** The server finalises the transaction by broadcasting a `DHCPACK`, confirming the lease. The client can now actively use the network.


![[Screenshot 2026-10-01 at 5.07.48 AM.png]]

The first two steps above can be skipped if a client remembers and wishes to reuse a previously allocated network address.


**The Mobility Flaw**

DHCP is fundamentally hostile to continuous mobility. Every time a mobile device physically moves to a different subnet, DHCP forces it to obtain a brand-new IP address. Because TCP connections are mathematically bound to specific IP addresses, moving between subnets instantly severs all active Transport-layer connections (e.g., dropping an active download or video call). In Chapter 7, we will learn how mobile cellular networks allow a host to retain its IP address and ongoing TCP connections as it moves between base stations in a provider’s cellular network.

### Network Address Translation (NAT)

With the explosion of Small Office/Home Office (SOHO) devices, ISPs cannot practically allocate large, contiguous blocks of globally unique IP addresses to every single home as the individual networks keep growing. **Network Address Translation (NAT)** has found increasingly widespread
use in such scenarios. Figure below shows the operation of a NAT-enabled router.

All four interfaces in the home network have the same subnet address of `10.0.0.0/24`. The address space `10.0.0.0/8 `is one of three portions of the IP address space that is reserved in for a private network, such as the home network below. These addresses are strictly local and only have meaning to devices within that network. Packets forwarded beyond the home network into the larger global Internet clearly cannot use these addresses (as source or destination) because there are many-many networks using this block of addresses.

![[Screenshot 2026-10-25 at 2.29.09 AM.png]]

So how is addressing handled when packets are sent to or received from the global Internet, where addresses are necessarily unique? The answer lies in NAT

The NAT-enabled router acts as an active middleman. To the outside world, the router behaves as a single device possessing one globally unique IP address (e.g., `138.76.29.7`). It effectively hides the entire internal home network. The router obtains this single public IP via DHCP from the ISP, while simultaneously running its own internal DHCP server to assign the `10.x.x.x` addresses to the home devices.


**The NAT Translation Table**

If all outbound traffic shares a single public IP, the router must have a way to route returning packets to the correct internal device. It solves this by utilising Layer 4 port numbers and a **NAT translation table**.

-  When an internal host (e.g., `10.0.0.1` using port `3345`) sends a request to a public web server, the NAT router intercepts the datagram. It replaces the private source IP with its public WAN IP (`138.76.29.7`) and generates a new, arbitrary source port (e.g., `5001`).

- The router logs the mapping (`10.0.0.1:3345` $\rightarrow$ `138.76.29.7:5001`) in its translation table.

- The external web server sends its reply to `138.76.29.7` on port `5001`. The router receives it, looks up port `5001` in its table, rewrites the destination IP and port back to `10.0.0.1:3345`, and forwards it into the home network.

- Because the port number field is 16 bits long, a single NAT router can multiplex over 65536 simultaneous connections behind its one public IP. The end devices don't have a public IP so the capacity of the internet is virtually increased.


**How NAT Reuses Ports (The 4-Tuple State Tracking):**

Textbooks often state that a NAT router is strictly limited to 65,536 simultaneous connections because the transport-layer port field is 16 bits. However, a modern router actually tracks connections using a complete **4-tuple**: `(Internal/Source IP, Internal/Source Port, Destination IP, Destination Port)`.  Because the remote destination server's IP and port are part of the unique connection signature, the router can reuse the exact same external NAT port (e.g., `5001`) simultaneously, provided the internal devices are talking to *different* external servers. *Example NAT Table with Port Reuse:*

| Internal IP | Internal Port | NAT (Public) IP | NAT Port | Destination IP (External)       | Dest Port |
| :---------- | :------------ | :-------------- | :------- | :------------------------------ | :-------- |
| `10.0.0.1`  | `3345`        | `138.76.29.7`   | `5001`   | `203.0.113.10` (Web Server A)   | `80`      |
| `10.0.0.2`  | `4444`        | `138.76.29.7`   | `5001`   | `142.250.190.46` (Web Server B) | `443`     |

**You might wonder:** Why include the "NAT (Public) IP" column in the table if a standard PAT router only has one public IP?  While it feels redundant for a typical home network, enterprise routers frequently manage a *pool* of multiple public IPs provided by their ISP.


**The 3 Types of NAT Implementations:**

- **Static NAT (1-to-1 Mapping):** A permanent, one-to-one mapping between a specific private IP and a specific public IP.  Used when you have an internal server (like a web or email server) that must always be reachable from the outside world at the exact same public IP address.

- **Dynamic NAT (Many-to-Many Mapping):** A router is given a pool of multiple public IP addresses. When internal devices need the internet, they temporarily check out an available public IP from the pool on a first-come, first-served basis. Large set of private address is mapped to a small set of public address dynamically. It does *not* use port numbers to multiplex.

- **PAT (Port Address Translation / NAT Overload):** A many-to-one mapping. This is the standard method used in all home routers. It maps multiple internal private IPs to a *single* public IP by using unique Layer 4 source port numbers to keep the connections separated.

If a local network only had a single public IP and assigned it via Static NAT, the rest of the network would be completely cut off from the internet. Network administrators mix and match NAT types using a block of multiple public IP addresses provided by their ISP.

- **The VIP Lane (Static NAT):** The admin takes one public IP (e.g., `138.76.29.8`) and permanently maps it to the company's internal web server, email server, or VPN gateway. This is mandatory because external clients on the internet need a guaranteed, unchanging public IP to connect to when they type in the company's website URL.

- **The General Pool (PAT):** The admin takes a _different_ public IP (e.g., `138.76.29.7`) and configures PAT (NAT Overload) on it. All the regular office computers (`10.0.0.1`, `10.0.0.2`, etc.) use this single address to browse the web, sharing it via port multiplexing.

### Port Forwarding (Destination NAT / DNAT)

* **Purpose:** Allows external clients on the internet to initiate a connection to a specific internal device (like a web server) hidden behind a private IP.
* It creates a permanent inbound mapping (like Static NAT) but uses specific Layer 4 port numbers so you don't need a dedicated secondary public IP.

    1. The router holds the single public IP; the internal server keeps its private IP (e.g., `192.168.1.50`).
    2. You configure the router to listen for specific traffic (e.g., "If packets hits the public IP on Port 80, forward them to `192.168.1.50`").
    3. When an external request arrives, the router rewrites the destination IP in the packet header from its own public IP to the server's private IP, passing the traffic inside. To the outside world, the router itself appears to be the web server.

The difference between Static Nat and Port Forwarding:

- **Static NAT (Entire IP Mapping):** Maps an entire private IP to a dedicated public IP. If you map `10.0.0.3` to `138.76.29.8`, _every single port_ on that public IP forwards directly to the internal server. It requires you to purchase a dedicated public IP from your ISP for every internal device you want to expose.

- **Port Forwarding (Specific Port Mapping):** Maps only a _single specific port_ (like Port 80) on a public IP to an internal private IP. It allows you to host a service without buying a second public IP, because the router continues to use all the other 65,535 ports on that same public IP for the rest of the network.

While Static NAT is essentially obsolete for everyday user devices and home networks, it remains useful in modern enterprise and cloud environments. Because external clients on the internet require a guaranteed, unchanging public IP to connect to, network administrators must use Static NAT to provide a permanent, one-to-one mapping for critical internal infrastructure.

- **Cloud Infrastructure (e.g., AWS Elastic IPs):** When a company spins up a production web server or database in AWS and assigns it a permanent public IP address, the virtual machine's operating system actually only holds a private IP. The cloud provider's edge routers use Static NAT to seamlessly map that external public IP directly to the internal server

- **Complex Enterprise Protocols:** Standard PAT modifies Layer 4 port numbers, which actively breaks certain protocols (like IPsec for site-to-site VPN gateways or SIP for enterprise VoIP telephony) that rely on strict, unaltered end-to-end port mappings. Static NAT provides the clean, untouched translation these fragile protocols require to function.

### Architectural Criticisms

While NAT successfully delayed IPv4 exhaustion, it fundamentally alters standard network architecture, leading to valid criticisms from engineers:

- **Protocol Layer Violations:** Routers should be strictly Layer 3 devices (processing only IP headers). NAT forces routers to inspect and modify Layer 4 (Transport) port numbers, destroying the end-to-end principle of direct, uninterrupted host-to-host communication.

- **Inbound Connection Failures:** Port numbers are designed to address processes, not to track hosts. Because internal devices lack public IPs, external peers cannot proactively initiate connections to them. This natively breaks server processes and P2P protocols running inside a home network, forcing developers to rely on complex **NAT traversal** tools just to establish basic peer connections.

### IPv6: Motivation and Origins

- Developed by the IETF in the early 1990s strictly because the 32-bit IPv4 address space was rapidly depleting due to exponential network growth. In February 2011, IANA officially allocated the last remaining central pool of unassigned IPv4 address blocks to regional registries.

- Beyond expanding the address space, designers used the transition to tweak and optimize network layer processing based on accumulated IPv4 operational experience.

- The version number 5 was intentionally skipped. It was originally reserved for the experimental ST-2 (Internet Stream protocol), which was eventually abandoned.

- **Length & Structure:** An IPv6 address is 128 bits long, written as eight 16-bit groups. The values are written in hexadecimal, and each 16-bit group (often referred to as a "hex-tet") is separated by colons rather than periods. As seen in network diagrams (e.g., `2001:DB8:0:1::1`), consecutive groups of zeros can be compressed into a double colon `::` to make the addresses easier to read and write.

When you see a shortened address, you simply apply two strict decompression rules to fill in the missing characters.

**Rule 1: Restore Leading Zeros:** Each group separated by a colon must contain exactly 4 characters. If a group has fewer than four, pad the front with zeros.

- `DB8` becomes `0DB8`
- `1` becomes `0001`.
- `0` becomes `0000`.

**Rule 2: Expand the Double Colon (`::`)** The `::` shorthand replaces consecutive groups of all zeros, but it can only be used _once_ per address (otherwise, a router wouldn't know how many zero groups belong to each double colon). To decode it, count the visible groups, subtract from 8, and replace the `::` with that many `0000` groups.

**Decoding the example from your slide (`2001:DB8:0:1::1`):**

1. **Count the visible groups:** We see 5 distinct groups (`2001`, `DB8`, `0`, `1`, and the final `1`).
2. **Calculate missing groups:** $8 - 5 = 3$. The `::` therefore hides exactly three groups of zeros.
3. **Insert the zero groups:** `2001:DB8:0:1:0:0:0:1`
4. **Restore leading zeros:** `2001:0DB8:0000:0001:0000:0000:0000:0001`

### IPv6 Datagram Format & Architecture

![[Screenshot 2026-10-01 at 1.53.59 PM.png]]

**1. Architectural Upgrades**

- **Expanded Addressing (128-bit):** Now every grain of sand is IP addressable.

- **Anycast Addresses:** A newly introduced address type. It allows a datagram to be routed to the nearest available host within a specific group. This feature could be used to send an HTTP GET to the nearest of a number of mirror sites that contain a given document. (To be covered in detail)

- **Fixed 40-Byte Header:** A new encoding of options allows for more flexible options processing.

- **Flow labelling:** IPv6 has not so easy to catch definition of a flow. RFC states that this allows labelling of packets belonging to particular flows for which the sender requests special handling, such as a non-default Quality of Service (QoS) or real-time service. For example, audio and video transmission might likely be treated as a flow. On the other hand, the more traditional applications, such as file transfer and e-mail, might not be treated as flows. It is possible that the traffic carried by a high-priority user (for example, someone paying for better service for their traffic) might also be treated as a flow.

**2. The IPv6 Header Fields**

- **Version (4 bits):** Identifies the version as `6`. (Note: Writing a `4` into this field does not create a valid IPv4 datagram)

- **Traffic Class (8 bits):** Functions like IPv4's TOS. It allows routers to prioritize specific datagrams within a flow, or favor certain applications over others (e.g., prioritizing real-time VoIP traffic over SMTP email).

- **Flow Label (20 bits):** The Flow Label does not give a packet high priority, it only gives it a unique ID. The actual priority level is set by the 8-bit **Traffic Class** field. If a core router is handling 1 million simultaneous flows, only a small fraction of them will actually have their Traffic Class set to high priority. The router uses the Flow Label simply to group packets together for high-speed hardware processing. Once the router reads the first packet of `Flow #12345` and sees its high-priority Traffic Class, it caches that forwarding decision in its silicon. When the next thousand packets arrive bearing that exact same Flow Label, the router instantly fast-tracks them without having to read the IPs, port numbers, or Traffic Class again.

- **Payload Length (16 bits):** An unsigned integer defining the size of the datagram excluding the 40-byte header.

- **Next Header (8 bits):** Identifies the upper-layer protocol (like TCP or UDP) to which the payload will be delivered (like IPv4's Protocol field). It just tells the system how to interpret the data starting at byte 41. Any extra routing or security instructions must be appended as separate blocks of data called **Extension Headers** inserted right after the IP header. That Extension Header will then contain its _own_ Next Header field pointing to the next block of data, creating a chain that eventually ends by pointing to the TCP or UDP payload. 

- **Hop Limit (8 bits):** Functions exactly like IPv4's TTL. Decremented by 1 at each router, if it hits zero, the datagram is dropped to prevent infinite routing loops.
- **Source & Destination Addresses:** 128 bits each.
- **Data (Payload):** When the datagram reaches its destination, the payload will be removed from the IP datagram and passed on to the protocol specified in the next header field.


**3. Hardware Optimizations (What Was Removed from IPv4)**

- **No Hardware Fragmentation:** IPv6 routers no longer fragment oversized packets. If a datagram exceeds the outgoing link's MTU, the router drops it and sends an ICMP "Packet Too Big" error back to the sender. This forces the end-systems to handle all fragmentation, stripping a heavy operation out of the core network routers.

- **No Header Checksum:** Because the Transport layer (TCP/UDP) and Link layer (Ethernet) already perform their own checksums, the network-layer checksum was deemed redundant. 

- **No Options:** Variable-length options are stripped from the main header. If options are needed, they are appended via the Next Header identifier.

### Transitioning from IPv4 to IPv6

**The Deployment Problem** 

While new IPv6 systems are designed to be backward-compatible with IPv4, IPv4 routers already deployed cannot process IPv6 datagrams. A **Flag Day** (a coordinated global network shutdown to upgrade all hardware simultaneously) is practically impossible at the Internet's scale.

**IPv6-in-IPv4 Tunneling** 

- When an IPv6 datagram reaches the boundary of an IPv4 network, the sending IPv6 router takes the _entire_ IPv6 datagram and encapsulates it directly into the data (payload) field of a standard IPv4 datagram. This IPv4 datagram addressed to the IPv6 node on the receiving side of the tunnel.

- The intervening IPv4 routers forward this packet normally based on its IPv4 header.

- The receiving IPv6 router at the other end of the tunnel gets the IPv4 packet. It identifies the hidden payload because the IPv4 header's **Protocol field is set to 41** (the dedicated code for an IPv6 payload). The router extracts the original IPv6 datagram and forwards it into the destination IPv6 network.

**Dual Stack Addressing (Coexistence Strategy)**

- **Application-Layer Agility:** Conversely, Application-Layer protocols (like HTTP or WebRTC) evolve and deploy rapidly because they only require end-users to install or update software at the edge of the network, without touching the core routing infrastructure.

### Generalized Forwarding & Software-Defined Networking (SDN)

**The Match-Plus-Action Paradigm** Traditional destination-based routing is strictly limited in scope: the router matches the Layer 3 Destination IP and executes a single action (forwarding to an output port).

Generalized forwarding expands this into a universal **match-plus-action** paradigm. A device can evaluate multiple header fields simultaneously across different protocol layers (Layer 2 MAC, Layer 3 IP, Layer 4 Ports) and execute a wide variety of actions. Because forwarding decisions may be made using network-layer and/or link-layer source and destination addresses, the forwarding devices shown below are more described as **packet switches** rather than layer 3 *routers* or layer 2 *switches*. 

![[Screenshot 2026-10-02 at 2.26.59 AM.png]]

SDN physically separates the logic from the hardware:

- **Data Plane (Local):** The packet switch simply executes the rules sitting in its local table.
- **Control Plane (Remote):** A physically decoupled, centralized remote controller computes, installs, and updates the match-plus-action tables across all packet switches in the network.

**The OpenFlow Flow Table**

OpenFlow, which is a foundational SDN standard, defines the generalized forwarding table (the **flow table**). This table essentially acts as an API, allowing administrators to program network-wide behaviors. Every entry in the flow table contains three core components:

1. **Match Fields:** A set of header values evaluated at hardware speed using TCAM (Ternary Content-Addressable Memory, with more than a million entries being possible). In practice, a flow table may be implemented by multiple flow tables for performance/cost reasons but we’ll focus here on the abstraction of a single flow table.

2. **Counters:** State-tracking variables, such as the number of packets matched by the entry and the timestamp of the last update.

3. **Actions:** The execution step. Based on the match, the switch can:
    - Forward the packet to a specific port (Routing)
    - Load-balance the packet across multiple ports
    - Duplicate and send to multiple ports (Multicasting)
    - Rewrite the header fields (NAT)
    - Drop the packet (Firewalling)

### OpenFlow: Mechanics of Generalized Forwarding

The OpenFlow standard mathematically defines exactly how the "Match-Plus-Action" table operates inside an SDN packet switch.

**1. The Match Phase**

Traditional routers only inspect Layer 3 IP headers. OpenFlow breaks the strict protocol layering by allowing the switch to simultaneously match against 12 different fields across three different protocol layers, plus the physical hardware port:

![[Screenshot 2026-10-02 at 2.41.12 AM.png]]

- The Ethernet type field corresponds to the upper layer protocol (e.g., IP) to which the frame’s payload will be de-multiplexed, and the VLAN fields will be covered later. 

- The ingress port refers to the input port at the packet switch on which a packet is received.

- This set of 12 values that can be matched in the OpenFlow 1.0 specification has grown to 41 values in more recent OpenFlow specifications

- OpenFlow intentionally restricts matching on fields like TTL or Datagram Length to prevent hardware complexity from ballooning.

- Flow tables also support wildcard entries (e.g., matching `10.3.*.*`). Each flow table entry also has an associated priority for when a packet matches multiple overlapping rules in the table.


**2. The Action Phase**

If a packet matches a rule, the switch executes a list of actions, in the order specified in the list. The three primary actions are:

- **Forwarding:** Send the packet to a specific output port, broadcast it, multicast it, or encapsulate the packet and send it up to the remote controller for software analysis. That controller then may (or may not) take some action on that packet, including installing new flow table entries, and may return the packet to the device for forwarding under the updated set of flow table rules.

- **Dropping:** If a match entry has a blank action list, the packet is dropped (this acts as a firewall rule).

- **Modify-Field:** The values in 10 packet-header fields (all layer 2, 3, and 4 fields shownabove except the IP Protocol field) may be re-written before the packet is forwarded to the chosen output port.

---
### What SDN Makes Possible (Examples)

A single OpenFlow flow table can replace an entire rack of specialized hardware:

- **Simple Forwarding (Layer 2/3 Switching):** Matching Destination IPs or MACs to forward traffic along a calculated path.

- **Source-Based Load Balancing:** In traditional IP routing, forwarding is _only_ based on the Destination IP. OpenFlow can match the _Source IP_ and route `Host A` over Link 1, while routing `Host B` over Link 2, perfectly balancing the load. This is impossible in legacy IP routing.

- **Firewalling:** Creating a rule that matches a specific subnet (e.g., `10.3.*.*`) with a Forward action, followed by a wildcard `*.*.*.*` rule with a Drop action, instantly turning the switch into a security boundary.

---
### Beyond OpenFlow: P4

While OpenFlow provides a strict, predefined set of match-and-action rules, it is still a limited API. The industry is currently moving toward **P4 (Programming Protocol-Independent Packet Processors)**. P4 is a higher level programming language (with variables, arithmetic, and conditional statements) designed specifically to write custom packet-processing logic that compiles directly into the switch's hardware silicon to run at line rate.

### Middleboxes and NFV

While traditional routers simply forward IP datagrams, a **middlebox** is defined as any intermediary device on the data path that performs functions apart from normal IP routing. Middleboxes generally fall into three categories:

1. **NAT Translation:** Rewriting IP addresses and ports to manage private addressing.
2. **Security Services:** Firewalls, Intrusion Detection Systems (IDS), and application-level gateways (like email spam filters) that block or inspect traffic.
3. **Performance Enhancement:** Web caches, TCP connection splitters, and load balancers that optimize delivery and distribute server requests.

#### Network Function Virtualization (NFV)

Historically, each middlebox was a specialized, proprietary piece of hardware, leading to high capital and operational costs. The modern industry trend is **Network Function Virtualization (NFV)**. Similar to the SDN philosophy, NFV replaces these proprietary hardware boxes with specialized software running on standard hardware (servers and storage), or outsources the functionality entirely to the cloud.

### The Architectural Debate: Purity vs. Pragmatism

#### The End-to-End Principle

For decades, Internet followed a strict philosophy defined in the famous *End-to-End Argument*

- The core network (routers) should be "dumb," focusing _exclusively_ on simple, fast IP datagram forwarding using only Layer 3 headers.
- All complex "intelligence" (reliability, error checking, application logic, state) must reside at the end-hosts (the smart endpoints).
- _Example:_ Because a router might crash and lose a packet, the network itself cannot guarantee delivery. Therefore, reliable data transfer _must_ be handled end-to-end by TCP at the hosts.

#### The Middlebox Violation

Middleboxes fundamentally violate the end-to-end principle. A NAT box rewrites Transport-layer ports; a firewall inspects Application-layer HTTP payloads; a TCP splitter intercepts and terminates end-host connections in the middle of the network.

Architectural purists view middleboxes as an abomination that breaks the layered model. Pragmatists argue that middleboxes exist because they fill critical operational, security, and address-scarcity needs that the original architecture failed to account for, meaning they are a permanent and growing fixture of the modern Internet.

### Routing Algorithms: Graph Abstraction & Classification

To compute forwarding tables, the control plane models the network as a weighted graph G,
- Nodes: The set of routers in the network
- Edges: The set of physical links connecting those routers 
- Link Cost: The numerical weight assigned to the direct link between node $x$ and node $x'$. If two nodes are not directly connected, $c(x, x') = \infty$. Cost metrics are configured by network administrators and can be static (always `1` for simple hop count), inversely proportional to link bandwidth, or dynamically tied to real-time link congestion/delay.

A routing algorithm determines the **least-cost path** (a sequence of routers with the minimum sum of link costs) between a source node and a destination node.

**Classification of Routing Algorithms**

| **Classification Axis** | **Type 1**                                                                                                                                                       | **Type 2**                                                                                                                                                                                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Information Scope**   | **Global (Link-State Algorithms):** Every router possesses complete information regarding the entire network topology and all link costs before computing paths. | **Decentralized (Distance-Vector Algorithms):** No router possesses a complete network map. A router only knows its physically connected neighbors and the direct link costs to them. Paths are computed iteratively by exchanging cost estimates with immediate neighbors. |
| **Adaptability**        | **Static:** Routes change very slowly over time, typically requiring manual intervention by a human administrator to edit tables.                                | **Dynamic:** Routes update automatically and rapidly via periodic exchanges or in immediate response to link cost/topology changes.                                                                                                                                         |

### Link-State (LS) Routing & Dijkstra's Algorithm

Link-State routing requires every node to hold an identical, complete map of the network topology and link costs.

- Each node discovers its immediate neighbours and costs, packages this into a Link-State packet, and floods (broadcasts) it to every other router in the network.

- Once the broadcast converges and all routers share the exact same topological database, each router independently runs Dijkstra with itself as the source node.

- For each destination node, the router traces the shortest-path tree from itself to the destination and extracts only the first-hop outgoing link.

- In an SDN architecture, the centralised SDN controller collects the link-state information, executes Dijkstra's algorithm on behalf of the switches, and pushes the resulting forwarding tables down to the data-plane hardware.

---
### Distance-Vector (DV) Routing Algorithm

Distance-Vector is a decentralised, iterative, asynchronous, and distributed algorithm based on Bellman-Ford equation. **Asynchronous** means that routers do not rely on a synchronized global clock to compute their routing tables or exchange messages. Let $d_x(y)$ be the cost of the actual least-cost path from node $x$ to node $y$:
$$d_x(y) = \min_v \{ c(x,v) + d_v(y) \}$$
where the minimum is taken over all directly attached neighbours $v$ of node $x$. The specific neighbour $v^*$ that yields this minimum becomes the next-hop router in $x$'s forwarding table for destination $y$. Each node $x$ maintains three pieces of local state:

- **Direct Link Costs:** $c(x,v)$ for each attached neighbuor $v$.

- **Its Own Distance Vector:** $D_x = [D_x(y) : y \in N]$, containing $x$'s current _estimate_ of the least cost to every node $y$ in the network.

- **Neighbours' Distance Vectors:** $D_v = [D_v(y) : y \in N]$ for every directly connected neighbor $v$.

**Protocol Execution Mechanics**

1. **Initialization:** For all destinations $y$, node $x$ sets $D_x(y) = c(x,y)$ if $y$ is a direct neighbour, and $D_x(y) = \infty$ otherwise. It initializes $D_w(y) = \infty$ for all neighbours $w$ and sends its initial vector $D_x$ to all immediate neighbours.

2. **Wait:** Node $x$ waits until it either detects a local link cost change to a neighbor OR receives an updated distance vector $D_w$ from a neighbor $w$.

3. **Recompute:** Node $x$ updates its own distance vector estimates for all $y \in N$ using: $$D_x(y) \leftarrow \min_v \{ c(x,v) + D_v(y) \}$$
4. **Notify:** Iff $D_x(y)$ changes for _any_ destination $y$, node $x$ transmits its newly updated distance vector $D_x$ to all of its immediate neighbours.

Under static conditions with no further link changes, these local estimates $D_x(y)$ converge to the true least costs $d_x(y)$.

When a link cost changes, the convergence speed of Distance-Vector depends entirely on whether the cost decreased or increased. Consider a 3-node topology ($x, y, z$) where $c(x,y) = 4$, $c(y,z) = 1$, and $c(x,z) = 50$. Initially, $D_y(x) = 4$ (direct) and $D_z(x) = 5$ (routed via $y$).

**1. Link Cost Decreases (Good News Travels Fast)**: 

Suppose $c(x,y)$ drops from `4` to `1`:

- **$t_0$:** Node $y$ detects the local link change, updates $D_y(x) = \min\{1+0, 1+5\} = 1$, and sends its updated vector to $z$.

- **$t_1$:** Node $z$ receives the update from $y$, recomputes $D_z(x) = \min\{50+0, 1+1\} = 2$, and sends its updated vector back to $y$.
- **$t_2$:** Node $y$ receives $z$'s vector, recomputes its table, sees no further changes to its least costs, and halts transmission. Convergence completes in 2 iterations.

**2. Link Cost Increases (Bad News Travels Slowly / Count-to-Infinity)**: 

Suppose $c(x,y)$ degrades from `4` to `60`:

- Before the link degrades, $D_y(x) = 4$ and $D_z(x) = 5$. Crucially, $z$'s path to $x$ goes _through_ $y$, but $y$'s distance table only records the scalar value $D_z(x) = 5$ without knowing that $z$'s underlying path relies on $y$.
- **$t_0$:** Node $y$ detects $c(x,y) = 60$ and recomputes $D_y(x)$ using its stored neighbor vector from $z$:$$D_y(x) = \min \{ c(y,x) + D_x(x), c(y,z) + D_z(x) \} = \min \{ 60 + 0, 1 + 5 \} = 6$$
- Node $y$ now sets its next-hop to $x$ as $z$, creating an immediate routing loop ($y$ routes to $z$, while $z$ routes to $y$), and advertises $D_y(x) = 6$ to $z$.

- **$t_1$:** Node $z$ receives $D_y(x) = 6$ and recomputes $D_z(x) = \min \{ 50 + 0, 1 + 6 \} = 7$, advertising `7` back to $y$.

- **$t_2$:** Node $y$ receives $D_z(x) = 7$ and recomputes $D_y(x) = \min \{ 60 + 0, 1 + 7 \} = 8$, advertising `8` back to $z$.

- This ping-pong loop continues for 44 iterations until $z$ finally computes a path cost via $y$ that exceeds its direct link cost $c(z,x) = 50$, at which point $z$ switches to its direct link to $x$ and the network stabilises. (If $c(z,x)$ were $\infty$, the nodes would increment their costs toward $\infty$ indefinitely).

**3. Loop Mitigation Techniques**

1. **Split Horizon:** A node never advertises a route back out of the interface from which it was learned.

2. **Split Horizon with Poisoned Reverse:** If node $z$ routes through node $y$ to reach destination $x$, node $z$ actively lies to $y$ by advertising $D_z(x) = \infty$ (while still advertising the true cost $D_z(x) = 5$ to all other neighbours). This prevents $y$ from ever attempting to route to $x$ via $z$. Limitation: Poisoned reverse only prevents 2-node ping-pong loops. Loops involving **3 or more nodes** are not detected by immediate neighbour poisoning.

3. **Triggered Updates:** Instead of waiting for the next periodic timer to expire, a router immediately transmits a DV update message the instant a metric changes, accelerating convergence.

### Comparison: Link-State (LS) vs. Distance-Vector (DV)

| **Metric**                                               | **Link-State (LS)**                                                                                                                                                                                                                                                                                                                                           | **Distance-Vector (DV)**                                                                                                                                                                                                                               |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Core Paradigm**                                        | _"Tell everyone about your neighbours."_ Every router builds the full topology map and runs Dijkstra locally.                                                                                                                                                                                                                                                 | _"Tell your neighbors about everyone."_ Every router relies on its neighbors' Bellman-Ford cost calculations.                                                                                                                                          |
| **Message Overhead**                                     | **High:** Requires flooding link-state packets across the entire network whenever a link cost changes.                                                                                                                                                                                                                                                        | **Low:** Messages are only exchanged between directly connected neighbors when local estimates change.                                                                                                                                                 |
| **Convergence Speed**                                    | **Fast:** Computes paths locally in $O(\vert{}N\vert{}^2)$ or $O(\vert{}N\vert{}\log\vert{}N\vert{})$ time without ping-pong loops.                                                                                                                                                                                                                           | **Slow:** Susceptible to routing loops and the count-to-infinity problem during link failures/degradations.                                                                                                                                            |
| **Robustness** (what happens when a router malfunctions) | **High (Contained Errors):** A malfunctioning router can advertise an incorrect cost for its _own_ attached links (because of bidirectional checks), but because every node computes its own tables independently, the calculation error does not corrupt the rest of the network's logic but might slight skew the network in case of wrongly emitted costs. | **Low (Error Propagation):** A malfunctioning router can advertise an incorrect least-cost path to _any_ destination. Because neighbours use each other's vectors to compute their own, a single corrupted table propagates across the entire network. |

### Hierarchical Internet Routing: Autonomous Systems (AS)

Treating the global Internet as a single, flat graph where every router executes the same routing algorithm is impossible in practice due to two constraints:

1. **Scale:** No router has the memory to store individual host/router entries, and flooding link-state updates or distance vectors globally would completely saturate link bandwidth.

2. **Administrative Autonomy:** The Internet is a network of networks. ISPs and enterprise administrators require control over how traffic is routed inside their own infrastructure and wish to hide their internal network topology from competitors.

**Autonomous Systems (AS)**

The Internet solves this by partitioning routers into regions called **ASes** each typically under the administrative control of a single entity (e.g., an ISP or large corporation):

- **Intra-AS Routing (Interior Gateway Protocols - IGP):** All routers within the _same_ AS run the exact same internal routing protocol (e.g., RIP or OSPF) to compute least-cost paths among internal routers. Different ASes can independently run completely different Intra-AS protocols.

- **Inter-AS Routing (Exterior Gateway Protocols):** Handles routing _between_ different ASes (globally standardized on **BGP**).

- **Populating the Forwarding Table:** A router's local forwarding table is configured collaboratively by _both_ Intra-AS and Inter-AS routing algorithms:

    - **Internal Destinations:** Entries are populated strictly by the **Intra-AS** routing algorithm.
    
    - **External Destinations:** If a router in $AS_1$ receives a packet destined for a subnet outside $AS_1$, it must forward the packet toward an **AS border (gateway) router** within $AS1$. The **Inter-AS** protocol learns which external prefixes are reachable via which border routers and propagates this reachability data across $AS_1$. Internal routers then combine this with their **Intra-AS** path costs to determine the next-hop interface toward the appropriate border router.

---
### Intra-AS Protocol: RIP (Routing Information Protocol)

RIP is a legacy Intra-AS routing protocol (originally bundled in the 1982 BSD-UNIX distribution) that implements the **Distance-Vector (Bellman-Ford)** algorithm.

**1. Metric & Scale Constraints**

- **Distance Metric:** Simple **hop count**, where every link has a uniform cost of `1`.
- **Hop Count Definition:** Measured as the number of **subnets** traversed from the source router to the destination subnet (including the destination subnet itself, a directly attached subnet has a cost of `1` hop).
- **Maximum Diameter ($\infty = 16$):** The maximum valid path cost in RIP is **15 hops**. A distance metric of **`16`** is defined as **infinity ($\infty$)** (unreachable). This bounds the count-to-infinity problem to a maximum of 16 iterations, but strictly limits RIP to small, localized Autonomous Systems with a diameter of 15 hops or fewer.
- **Advantages:** Simple to configure and minimal communication overhead.
- **Disadvantages:** Slow convergence times (susceptible to the count-to-infinity problem during link failures) and limited network diameter.


**2. Advertisements & Protocol Mechanics**

- **Periodic Exchange:** Neighbouring routers exchange distance vectors every **30 seconds** using RIP **Response Messages** (called _advertisements_).
- **Payload Capacity:** Each RIP advertisement carries a list of up to **25 destination subnets** (in CIDR prefix format for RIPv2) within the AS, along with the sender's hop count to each subnet.
- **Table Update Execution:** If Router $D$ receives an advertisement from neighbour $A$ claiming $A$ can reach subnet $z$ in `4` hops, $D$ applies the Bellman-Ford equation ($1 + 4 = 5$ hops via $A$). If $D$'s current path to $z$ via neighbour $B$ is `7` hops, $D$ overwrites its routing table entry to route toward $z$ via next-hop $A$ with a new cost of `5`.


**3. Failure Detection & Recovery**

- **180-Second Dead Timer:** If a router does not hear a RIP advertisement from a neighbour for **180 seconds** (6 missed 30-second intervals), it declares that neighbour or the connecting link dead.
- **Invalidation:** The router invalidates all routes that use that dead neighbour as a next hop (setting their distance to `16`), recomputes its table, and immediately sends triggered advertisements to its remaining neighbours.
- **Loop Prevention:** RIP mandates **Split Horizon with Poisoned Reverse** (advertising a metric of `16` back out the interface from which a route was learned) and **Triggered Updates** on metric changes.


**4. Transport Encapsulation & Application-Layer Execution**

- **Application-Layer Daemon (`routed`):** Although RIP is a Network-Layer (Control Plane) protocol by function, it is implemented as a user-space **application-layer process** (such as the `routed` daemon in UNIX).

- **UDP Encapsulation (Port 520):** The `routed` process encapsulates RIP advertisements inside standard **UDP segments on Port 520**, which are then passed down to the IP layer for transmission. Reliable transport (TCP) is unnecessary because advertisements are periodically repeated every 30 seconds. When the `routed` daemon computes a new shortest path, it uses OS kernel system calls to push the updated entries down into the kernel's network-layer **Forwarding Table**.

- **RIPv2 Message Format:** Contains a header (`Command`, `Version`, `Reserved`) followed by up to 25 repeating route blocks, each specifying: `Address Family`, `Route Tag`, `Network Address`, `Subnet Mask` (enabling CIDR support, unlike classful RIPv1), `Next-Hop Address`, and `Distance` ($1\text{--}16$).

- **Multicast Delivery:** RIPv2 routers broadcast/multicast updates to attached LANs using the reserved `224.0.0.0/4` multicast range (specifically `224.0.0.9` in standard RIPv2 implementations; `224.0.0.0` base entry in UNIX routing tables).

### Intra-AS Protocol: OSPF (Open Shortest Path First)

OSPF is a **link-state** protocol (Dijkstra, see Link-State Routing above) used for Intra-AS routing. Every router periodically **floods its immediate reachability information** (the state of its attached links and networks) to all other routers in the AS. All routers therefore hold the same map and each computes its own shortest paths.

- **Distance metric:** An **administrative weight** configured per link, not a hop count as in RIP.
- **Deriving the weight from bandwidth:** A common choice is $\text{cost} = \dfrac{\text{reference bandwidth}}{\text{link bandwidth}}$. With a reference of 100 Mbps, a 10 Mbps link costs 10 and a 1 Gbps link costs 0.1. Costs are integers, so a 1 Gbps link would round up to 1 and look the same as a 100 Mbps link, which is why the reference bandwidth is raised above the fastest link (e.g., to 10 Gbps).

**Information Flow**

| **Term** | **Meaning** |
| :--- | :--- |
| **State** | Per-router information about itself and its attached networks |
| **OSPF advertisements** | Propagate the state to all routers |
| **Link state database (LSDB)** | The state of all routers |
| **Topology map** | A directed graph with link costs, derived from the LSDB, on which Dijkstra runs |

**OSPFv2 Components**

| **Question** | **Mechanism** |
| :--- | :--- |
| Who is my neighbour? | **Hello protocol** |
| With whom do I want to talk (on a LAN)? | **Designated router (DR)** and **Backup designated router (BDR)** |
| What information am I missing? | **Database synchronization** |
| How do I distribute information? | Advertisements are disseminated to the **entire** AS by **reliable flooding**. OSPF messages are carried **directly over IP**, not over TCP or UDP. |
| How do I compute routes? | Dijkstra on the LSDB. Supports **equal-cost multipath**. |

#### Neighbour Discovery: The Hello Protocol

**Purpose**

- Ensures **bi-directional communication**: neighbours can both send to and receive from each other.
- Ensures neighbours **agree on parameters** (`HelloInterval` and `RouterDeadInterval`). Routers whose values differ do not become neighbours.

**How**

- A **Hello packet** is sent to a fixed, well-known **multicast address**, and Hellos are sent **periodically**.
- On a broadcast network, a designated router is elected.
- **Defaults:** `HelloInterval` = 10 seconds, `RouterDeadInterval` = 4 × `HelloInterval` = 40 seconds. A neighbour not heard from within `RouterDeadInterval` is declared dead.

**OSPF Multicast Addresses**

| **Address** | **Name** | **Used for** |
| :--- | :--- | :--- |
| `224.0.0.5` | AllSPFRouters | All OSPF routers |
| `224.0.0.6` | AllDRouters | The designated and backup designated routers |

For OSPFv3 (IPv6) the equivalents are `FF02::5` and `FF02::6`.

**Neighbour States**

| **State** | **Meaning** |
| :--- | :--- |
| **Down** | The neighbour is considered dead. No communication at all. |
| **Init** | "I have heard of a neighbour". **Uni-directional** communication. |
| **TwoWay / ExStart** | Communication is **bi-directional**. |

A router moves out of Init when it finds its own Router ID listed in the neighbour list of the neighbour's Hello, since this shows that the neighbour received its Hello. Database synchronization starts at ExStart.

**Designated Router**

On a LAN with $n$ routers, forming an adjacency between every pair would require $\frac{n(n-1)}{2}$ database exchanges. Instead, a DR and a BDR are elected (highest **Router Priority** wins, ties are broken by Router ID). Every other router synchronizes and exchanges updates only with the DR and BDR (sent to `224.0.0.6`), and the DR floods them to all routers on the LAN (`224.0.0.5`). The BDR takes over if the DR fails.

**Hello Packet Format**

| **Field** | **Purpose** |
| :--- | :--- |
| Version, Type (= 1), Packet length | Common OSPF header |
| **Router ID** | Identifies the sending router |
| **Area ID** | The area the interface belongs to |
| Checksum, **AuType**, **Authentication** | Integrity check and authentication of the message |
| Network Mask | Mask of the interface on which the Hello is sent |
| **HelloInterval**, **RouterDeadInterval** | Timers, must match on both sides |
| Options | Capabilities of the router |
| **Router Priority** | Used in DR election |
| **Designated Router**, **Backup Designated Router** | Current DR and BDR on the network |
| **Neighbour list** (Neighbor A, B, ...) | Routers from which a Hello has recently been heard |

#### OSPF Packets

- Carried **directly in IP** with protocol number **89**.
- Sent to neighbours using a **multicast address** with **TTL = 1**, so they never travel beyond the local link.

**Five packet types**

| **Type** | **Role** |
| :--- | :--- |
| **Hello** | Neighbour discovery and maintenance |
| **Database Description (DD)** | Summarises the LSDB (LSA headers) during initial synchronization |
| **Link State Request** | Asks a neighbour for specific LSAs |
| **Link State Update** | Carries the LSAs themselves (used for flooding) |
| **Link State Acknowledgement** | Acknowledges received LSAs |

#### Link State Database and LSAs

The LSDB is each router's local view of the topology. It consists of **Link State Advertisements (LSAs)**, where an LSA is a data unit describing the local state of a router or network. The LSDB **must be kept synchronized** across routers so that they react consistently to failures.

**Example LSDB** (routers `10.1.1.1` to `10.1.1.6`, one **Router-LSA** each):

| **LS-Type** | **Link State ID** | **Adv. Router** | **Checksum** | **Seq. No.** | **Age** |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Router-LSA | 10.1.1.1 | 10.1.1.1 | `0x9b47` | `0x80000006` | 0 |
| Router-LSA | 10.1.1.2 | 10.1.1.2 | `0x219e` | `0x80000007` | 1618 |
| Router-LSA | 10.1.1.3 | 10.1.1.3 | `0x6b53` | `0x80000003` | 1712 |
| Router-LSA | 10.1.1.4 | 10.1.1.4 | `0xe39a` | `0x8000003a` | 20 |
| Router-LSA | 10.1.1.5 | 10.1.1.5 | `0xd2a6` | `0x80000038` | 18 |
| Router-LSA | 10.1.1.6 | 10.1.1.6 | `0x05c3` | `0x80000005` | 1680 |

**LSA Header (20 bytes)**

| **Field** | **Size** | **Role** |
| :--- | :--- | :--- |
| LS Age | 16 bits | Seconds since the LSA was originated |
| Options | 8 bits | Optional capabilities |
| LS Type | 8 bits | Kind of LSA (e.g., Router-LSA) |
| Link State ID | 32 bits | Identifies the piece of the topology being described |
| Advertising Router | 32 bits | Router that originated the LSA |
| LS Sequence Number | 32 bits | Distinguishes instances of the same LSA |
| LS Checksum | 16 bits | Verifies the LSA contents |
| Length | 16 bits | Length of the LSA including the header |

**Roles of the Header Fields**

- **Identifying an LSA:** The triple (**LS Type**, **Link State ID**, **Advertising Router**).
- **Verifying contents:** The **LS Checksum**.
- **Identifying an LSA instance** (the topology changes, so the same LSA is re-originated): The **LS Sequence Number**, in a linear sequence space. The higher number is the newer instance. Reaching the maximum sequence number starts a new instance.

**LS Age (Ensuring Consistency)**

- Goal: a **new sequence number every 30 minutes** (the originating router refreshes its LSA).
- Maximum value is **1 hour**. An LSA with age > 1 hour is invalid and is removed.
- This allows **premature aging**: a router can flood an LSA with its age set to the maximum to withdraw it from every database.
- Together this ensures removal of outdated information, e.g., LSAs of a router that has died and can no longer refresh them.

In the example, ages are in seconds, so an LSA at 1712 s (about 28.5 minutes) is about to be refreshed at 1800 s.

**Router-LSA Body**

After the 20-byte header, a Router-LSA carries:

- Flags **V** (virtual link endpoint), **E** (AS boundary router), **B** (area border router).
- The **number of links** ($\#$ Link).
- For each link: **Link ID**, **Link Data**, **Type**, **number of TOS metrics**, and the **Metric** (the link cost).

---
#### Database Synchronization

**Central aspect:** all routers need **identical** databases.

**Quick check:** Two databases are considered synchronized if they have the same number of LSAs and the sums of the LS Checksums of the LSAs are equal.

| **Type** | **When** | **How** |
| :--- | :--- | :--- |
| **Initial synchronization** | After Hello, once bi-directional communication exists | **Explicit transfer** of the database upon establishment of neighbour-ship: all **LS headers** are sent to the neighbour in **Database Description (DD)** packets. A router then requests the LSAs it is missing or has older versions of (Link State Request) and receives them in Link State Updates. |
| **Continuous synchronization** | For the lifetime of the adjacency | **Flooding** of all future LSAs |

**Reliable Flooding**

When a router originates a new LSA or receives a newer one, it floods it out of all its interfaces except the one it arrived on.

- Example: `10.1.1.3` sends an **LS Update**, and every router re-floods it to its neighbours.
- Receiving the **same copy of an LSA** back from a neighbour is an **implicit ACK**.
- **Delayed ACKs** are used: acknowledgements are batched instead of sent per LSA.
- **All LSAs must be acknowledged**, either implicitly or explicitly.

**Robustness of Flooding**

- More robust than flooding along a **spanning tree**, since every link is used and there is no tree to repair when a link fails.
- LSAs are **refreshed every 30 minutes**.
- LSAs have **checksums**, are **aged**, and **cannot be sent at an arbitrary rate**, since timers limit them.

**LSA Timers**

| **Timer** | **Value** | **Role** |
| :--- | :--- | :--- |
| `MinLSArrival` | 1 second | Minimum time between accepting two instances of the same LSA |
| `MinLSInterval` | 5 seconds | Minimum time between originating two instances of the same LSA |
| `CheckAge` | 5 minutes | How often the checksums of LSAs in the database are verified |
| `MaxAgeDiff` | 15 minutes | Largest age difference at which two instances are still treated as the same age |
| `LSRefreshTime` | 30 minutes | How often an originating router refreshes its LSAs |
| `MaxAge` | 1 hour | Age at which an LSA is invalid and removed |

#### Routing Table Calculation

The LSDB is a **directed graph with a cost on each link**. Each router runs Dijkstra's SPF algorithm with itself as the root:

1. Add the root router to the shortest-path tree.
2. Add all its neighbours to the **candidate list**.
3. Move the candidate with the smallest cost into the tree.
4. Add that router's neighbours to the candidate list if they are not yet on it, or if the new cost is smaller.
5. Repeat until the candidate list is empty.

**Example (root = `10.1.1.3`)**

Links: $1\text{-}2$: 3, $1\text{-}3$: 5, $2\text{-}3$: 3, $2\text{-}4$: 1, $3\text{-}5$: 1, $4\text{-}5$: 3, $4\text{-}6$: 6, $5\text{-}6$: 10 (written with the last octet only, all costs are the same in both directions). Entries are (cost, next hop).

| **Step** | **Added to tree** | **Candidate list afterwards** |
| :--- | :--- | :--- |
| Start | `.3` | `.5` (1, .5), `.2` (3, .2), `.1` (5, .1) |
| 1 | `.5` (cost 1) | `.2` (3, .2), `.4` (4, .5), `.1` (5, .1), `.6` (11, .5) |
| 2 | `.2` (cost 3) | `.4` (4, **.5 and .2**), `.1` (5, .1), `.6` (11, .5) |
| 3 | `.4` (cost 4) | `.1` (5, .1), `.6` (**10**, .5 and .2) |
| 4 | `.1` (cost 5) | `.6` (10, .5 and .2) |
| 5 | `.6` (cost 10) | empty |

- **Step 2:** `.4` is reached with cost 4 both via `.5` ($1 + 3$) and via `.2` ($3 + 1$), so both next hops are kept. This is **equal-cost multipath**. Also, going to `.1` via `.2` costs $3 + 3 = 6$, which is worse than the direct 5, so it is not updated.
- **Step 3:** `.6` improves from 11 (via `.5` directly, $1 + 10$) to 10 (via `.4`, $4 + 6$).

**Resulting routing table at `10.1.1.3`**

| **Destination** | **Cost** | **Next hop** |
| :--- | :--- | :--- |
| `10.1.1.1` | 5 | `10.1.1.1` |
| `10.1.1.2` | 3 | `10.1.1.2` |
| `10.1.1.4` | 4 | `10.1.1.5` or `10.1.1.2` |
| `10.1.1.5` | 1 | `10.1.1.5` |
| `10.1.1.6` | 10 | `10.1.1.5` or `10.1.1.2` |

#### OSPF: Advanced Features, Summary and Comparison

**Advanced features**

- **Security:** All OSPF messages are authenticated to prevent malicious intrusion, using the `AuType` and `Authentication` fields of the header (a password or a cryptographic digest, i.e., a MAC, see Network Security). Without it, Trudy could inject false LSAs and corrupt every router's map.
- **Multiple same-cost paths** are allowed. For each link, multiple cost metrics can be kept for different **types of service (TOS)**, e.g., a satellite link is given a low cost for best-effort traffic and a high cost for real-time traffic.
- **Integrated unicast and multicast support:** Multicast OSPF (**MOSPF**) uses the same topology database as OSPF.
- **Hierarchical OSPF** in large domains: the AS is split into **areas** (the Area ID in the header) connected through a backbone area, so that flooding and the LSDB are limited to an area. This keeps the size of the LSDB manageable.

**Summary**

- Link-state protocol (based on Dijkstra). Routers periodically flood immediate reachability information to all other routers. Metric is the administrative weight.
- **Advantage:** Fast convergence.
- **Disadvantage:** Complexity and communication overhead.

**RIP vs. OSPF**

| | **RIP** | **OSPF** |
| :--- | :--- | :--- |
| **Algorithm** | Distance-Vector (Bellman-Ford) | Link-State (Dijkstra) |
| **Metric** | Hop count | Administrative weight |
| **What is exchanged** | A distance vector, only with direct neighbours | LSAs, flooded to every router in the AS |
| **Convergence** | Slow, count-to-infinity | Fast |
| **Carried over** | UDP port 520 (application-layer daemon) | Directly over IP (protocol 89) |
| **Overhead** | Low | Higher |

**Other Intra-AS routing protocols**

| **Protocol** | **Type** |
| :--- | :--- |
| **IS-IS** (Intermediate-System-to-Intermediate-System) | ISO 10589, link-state |
| **IGRP** (Interior Gateway Routing Protocol) | Cisco proprietary, distance-vector |
| **EIGRP** (Enhanced IGRP) | Cisco proprietary, enhanced distance-vector |
