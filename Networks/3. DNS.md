### Services Provided by DNS

We need a directory service that translates hostnames to IP addresses which is the main task of the Internet’s domain name system (DNS). It is:

1. A distributed database implemented in a hierarchy of DNS servers,
2. An application-layer protocol that allows hosts to query the distributed database. 

The DNS servers are often UNIX machines running the Berkeley Internet Name Domain (BIND) software.  

To translate a hostname to an IP address, applications will invoke the client side of DNS, specifying the hostname that needs to be translated. On many UNIX-based machines, `gethostbyname()` function call does this. DNS in the user’s host then takes over, sending a query message into the network. All DNS query and reply messages are sent within UDP datagrams to port 53. DNS in the user’s host receives a DNS reply. This is then passed to the invoking application. 

So DNS adds an additional delay to the Internet applications that use it. Fortunately, the desired IP address is often cached in a nearby DNS server, which helps to reduce DNS delay/traffic. 

Like HTTP, FTP, and SMTP, the DNS protocol is an application-layer protocol since it runs between communicating end systems using the client-server paradigm. 

DNS provides a few other important services in addition to translating hostnames to IP addresses:

- **Host aliasing**: A host with a complicated hostname can have one or more alias names. For example, a hostname such as `relay1.west-coast.enterprise.com` could have, say, two aliases such as `enterprise.com` and` www.enterprise.com`. In this case, the hostname `relay1.west-coast.enterprise.com` is said to be a canonical hostname. DNS can be invoked by an application to obtain the canonical hostname for a supplied alias hostname as well as the IP address of the host.

- **Mail server aliasing**: Bob has an account with Yahoo Mail, Bob’s e-mail address might be as simple as `bob@yahoo.com`. However, the hostname of the Yahoo mail server is more complicated and much less mnemonic than simply `yahoo.com`. DNS can be invoked by a mail application to get the IP address of the host. In fact, the MX record (see below) permits a company’s mail server and Web server to have identical (aliased) hostnames. For example, a company’s web server and mail server can both be called `enterprise.com`.

- **Load distribution**: DNS is also used to perform load distribution among replicated servers, such as replicated Web servers. Busy sites are replicated over multiple servers, with each server running on a different end system and each having a different IP address. For replicated Web servers, a set of IP addresses is thus associated with one alias hostname. The DNS database contains this set of IP addresses. When clients make a DNS query for a name mapped to a set of addresses, the server responds with the entire set of IP addresses, but rotates the ordering of the addresses within each reply so it distributes the traffic among the replicated servers. DNS rotation is also used for e-mail so that multiple mail servers can have the same alias name. Also, content distribution companies such as Akamai have used DNS in more sophisticated ways to provide Web content distribution (see below).

### Design Considerations

A simple design for DNS would have one DNS server that contains all the mappings. In this centralised design, clients simply direct all queries to the single DNS server, and the DNS server responds directly to the querying clients. The problems with a centralized design include:

- A single point of failure: If the DNS server crashes, so does the entire Internet
- Traffic volume: A single DNS server would have to handle all DNS queries (for all the HTTP requests and e-mail messages generated from hundreds of millions of hosts).
- Distant centralised database. A single DNS server cannot be “close to” all the querying clients. This can lead to significant delays.
- Maintenance. The single DNS server would have to keep records for all Internet hosts. This database would be huge and would have to be updated frequently to account for every new host.

### Hierarchy of DNS Servers

DNS uses a large number of servers, organised in a hierarchical fashion and distributed around the world. No single DNS server has all of the mappings for all of the hosts in the Internet. Name Servers are the machines that store the distributed database and respond to queries. The three main classes of Name Servers are organized in a heirarchy as shown below.

1. Root DNS server
2. Top-level domain (TLD) DNS servers
3.  Authoritative DNS servers

![[Screenshot 2026-09-08 at 9.41.53 PM.png]]

Suppose a DNS client wants to determine the IP address for the hostname` www.amazon.com`. The client first contacts one of the root servers, which returns IP addresses for TLD servers for the top-level domain `com`. The client then contacts one of these TLD servers, which returns the IP address of an authoritative server for `amazon.com`. Finally, the client contacts one of the authoritative servers for `amazon.com`, which returns the IP address for the hostname `www.amazon.com`. 

- **Root DNS servers**: 
	There are more than 1000 root servers instances scattered all over the world. These root servers are copies of 13 different root servers, managed by 12 different organisations, and coordinated through the Internet Assigned Numbers Authority (IANA). So any system can store the 13 IP addresses (which are routed to the nearest copy of the server) to kick start the searching journey. Root name servers provide the IP addresses of the TLD servers.

- **Top-level domain (TLD) servers:** These servers manage the domains just below the root zone. They are divided into specific categories:

	- **Generic TLDs (gTLDs):** Standard domains like .com, .org, .net, .edu, and .gov.
	- **Country code TLDs (ccTLDs):** Geographic domains like .uk, .fr, .in, and .us.
	- **New gTLDs:** Launched in 2013, adding over 1,300 new custom suffixes like .dev, .online, .google, and .nyc.
	- **Infrastructure TLD:** Exclusively used for technical network routing purposes (.arpa).
	
	Different TLD name servers are maintained by different institutions. For example, `Verisign Global Registry Services` maintains the TLD servers for the `.com` gTLD, while `Educause` maintains the `.edu` gTLD. The network infrastructure supporting a TLD can be large and complex, and their primary job is to provide the IP addresses for authoritative DNS servers.
	
	**Second-Level Domain (SLD) Servers:** These servers are responsible for domains situated just below the top-level domain zone, such as example.com or amazon.com. Different institutions maintain their own SLD name servers. Note that domains like `.co.in` or `.co.uk` are technically second-level domains, but are treated by software as "effective TLDs" (eTLDs).

- **Authoritative DNS servers:** 
	Every organisation with publicly accessible hosts (such as Web servers and mail servers) on the Internet must provide publicly accessible DNS records that map the names of those hosts to IP addresses. An organisation’s authoritative DNS server houses these DNS records. An organisation can choose to implement its own authoritative DNS server to hold these records. Alternatively, a organisation can pay to have these records stored in an authoritative DNS server of some service provider. Most universities and large companies implement & maintain their own primary & secondary (backup) authoritative DNS server.

There is another important type of DNS server called the local DNS server (also known as a default name server). It does not strictly belong to the authoritative hierarchy of servers. Instead, it acts as a proxy that takes the initial query from the user and performs the heavy lifting of navigating the global DNS hierarchy on the user's behalf.

### **Resolver Architecture**

- **Stub Resolver:** Client-side software running directly on your local machine that extracts hostnames, sends initial queries, and returns final answers to the application.

- **Forwarding Resolver:** Software running on intermediate hardware (such as your home Wi-Fi router) that acts as a proxy, receiving queries from the stub resolver and forwarding them onward to a recursive resolver.

- **Recursive Resolver:** The heavy lifter hosted by your ISP (residential, corporate, or university) that receives recursive queries from forwarding/stub resolvers and systematically issues iterative queries to the root, TLD, and SLD name servers before returning the final answer.

Each ISP, whether residential or institutional, provides hosts with the IP addresses of one or more of its local recursive resolvers when they connect to the network (typically via DHCP). A host’s local DNS server is usually geographically or topologically close to the host. For an institutional ISP, it may be on the exact same LAN. For a residential ISP, it is typically separated from the host by no more than a few routers.

![[Screenshot 2026-09-08 at 10.00.19 PM.png]]

Suppose the host `cse.nyu.edu` desires the IP address of `gaia.cs.umass.edu.` Also suppose that NYU’s local DNS server for` cse.nyu.edu` is called `dns.nyu.edu` and that an authoritative DNS server for `gaia.cs.umass.edu` is called `dns.umass.edu`. The host `cse.nyu.edu` first sends a DNS query message to its local DNS server, `dns.nyu.edu`. The query message contains the hostname to be translated, namely, `gaia.cs.umass.edu`. The local DNS server forwards the query message to a root DNS server. The root DNS server takes note of the `edu` suffix and returns to the local DNS server a list of IP addresses for TLD servers responsible for edu. The local DNS server then resends the query message to one of these TLD servers. The TLD server takes note of the `umass.edu` suffix and responds with the IP address of the authoritative DNS server for the University of Massachusetts, namely, `dns.umass.edu`. Finally, the local DNS server resends the query message directly to `dns.umass.edu`, which responds with the IP address of `gaia.cs.umass.edu`. So, in order to obtain the mapping for one hostname, eight DNS messages were sent, four query messages and four reply message.

In some cases, the TLD server may know only of an intermediate DNS server, which in turn knows the authoritative DNS server for the hostname. Suppose that each of the departments at the University of Massachusetts has its own DNS server, and that each departmental DNS server is authoritative for all hosts in the department. In this case, when the intermediate DNS server, `dns.umass.edu`, receives a query for a host with a hostname ending with `cs.umass.edu`, it returns to `dns.nyu.edu` the IP address of `dns.cs.umass.edu`. The local DNS server `dns.nyu.edu` then sends the query to the authoritative DNS server, which returns the desired mapping to the local DNS server, which in turn returns the mapping to the requesting host. In this case, a total of 10 DNS messages are sent. 

The example shown above makes use of both recursive queries and iterative queries. The query sent from `cse.nyu.edu` to `dns.nyu.edu` is  recursive, since the query asks `dns.nyu.edu` to obtain the mapping on its behalf. However, the subsequent three queries are iterative since all of the replies are directly returned to dns.nyu.edu. In theory, any DNS query can be iterative or recursive. The figure below shows a DNS query chain for which all of the queries are recursive. In practice, the queries typically follow the pattern above: The query from the requesting host to the local DNS server is recursive, and the remaining queries are iterative.

### DNS Caching

In a query chain, when a DNS server receives a DNS reply (containing, for example, a mapping from a hostname to an IP address), it can cache the mapping in its local memory. Because hosts and mappings between hostnames and IP addresses are by no means permanent, DNS servers discard cached information after a period of time (often set to two days). A local DNS server can also cache the IP addresses of TLD servers, thereby allowing the local DNS server to bypass the root DNS servers in a query chain. In fact, because of caching, root servers are bypassed for almost all DNS queries.

### DNS Records

DNS servers store Resource Records (RRs) formatted as a four-tuple: `(Name, Value, Type, TTL)`. The **TTL** (Time to Live) dictates exactly when the record expires from a cache, while the interpretation of the **Name** and **Value** fields depends entirely on the **Type**.

| **Record Type** | **Name Field**                 | **Value Field**                      | **Purpose**                                                                                     |
| --------------- | ------------------------------ | ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| **A**           | Standard hostname              | 32-bit IPv4 address                  | Standard hostname-to-IP resolution.                                                             |
| **AAAA**        | Standard hostname              | 128-bit IPv6 address                 | IPv6 hostname-to-IP resolution.                                                                 |
| **NS**          | Broad domain (e.g., `foo.com`) | Hostname of authoritative DNS server | Routes queries further down the DNS hierarchy to the server that knows the IPs for that domain. |
| **CNAME**       | Simplified alias               | Canonical hostname                   | Maps an alias to its true, complex hostname.                                                    |
| **MX**          | Domain alias                   | Canonical hostname of mail server    | Allows a company to have a simpler alias for mail server                                        |
 
Note that by using the MX record, a company can have the same aliased name for its mail server and for one of its other servers (such as its Web server). To obtain the canonical name for the mail server, a DNS client would query for an MX record, to obtain the canonical name for the other server, the DNS client would query for the A/CNAME record.

**Note:**

- If a DNS server is authoritative for a particular hostname, then the DNS server will contain a Type A record for the hostname (even if the DNS server is not authoritative, it may contain a Type A record in its cache).

- If a server is not authoritative for a hostname, then the server will contain a Type NS record for the domain that includes the hostname and a Type A record that provides the IP address of the DNS server in the Value field of the NS record.

Example: Suppose an edu TLD server is not authoritative for the host `gaia.cs.umass.edu`/ Then this server will contain a record for a domain that includes the host `gaia.cs.umass.edu`: `(umass.edu, dns.umass.edu, NS)`. The edu TLD server would also contain a Type A record, which maps the DNS server `dns.umass.edu` to an IP address: `(dns.umass.edu, 128.119.40.111, A)`.

### DNS Messages

These are only two kinds of DNS messages: Query and Reply. Furthermore, they have the same format, as shown below. The semantics of the various fields in a DNS message are as follows:

The first 12 bytes is the header section, which has a number of fields. 
The first field is a 16 bit number that identifies the query. This identifier is copied into the reply message to a query, allowing the client to match received replies with sent queries. 
There are a number of flags in the flag field. 
- A 1-bit query/reply flag indicates whether the message is a query (0) or a reply (1).
- A 1-bit authoritative flag is set in a reply message when a DNS server is an authoritative server for a queried name. 
- A 1-bit recursion-desired flag is set when a client (host or DNS server) desires that the DNS server perform recursion when it doesn’t have the record. 
- A 1-bit recursion-available field is set in a reply if the DNS server supports recursion. 


![[Screenshot 2026-09-08 at 11.08.09 PM.png]]

In the header, there are also four number-of fields. These fields indicate the number of occurrences of the four types of data sections that follow the header.

1. The question section contains information about the query that is being made. This section includes:
	1. A name field that contains the name that is being queried
	2. A type field that indicates the type of question being asked about the name, for example, a host address associated with a name (Type A) or the mail server for a name (Type MX).

2. In a reply from a DNS server, the answer section contains the resource records for the name that was originally queried. A reply can return multiple RRs in the answer, since a hostname can have multiple IP addresses (for example, for replicated Web servers, as discussed earlier).

3. The authority section contains records of other authoritative servers (NS responses), in case you had asked for A responses.

4. The additional section contains other helpful records. For example, the answer field in a reply to an MX query contains a resource record providing the canonical hostname of a mail server. The additional section contains a Type A record providing the IP address for the canonical hostname of the mail server.

You can send a DNS query message to some DNS server with the nslookup program, which is available on most Windows and UNIX platforms. For e.g., from a Windows host, open the Command Prompt and type `nslookup`. Now you can send a DNS query to any DNS server. After receiving the reply message from the DNS server, nslookup will display the records included in the reply (in a human-readable format). As an alternative to running nslookup from your own host, you can visit one of many Web sites that allow you to remotely employ nslookup.

### How records get into the database?

Suppose you have a new startup` Network Utopia`. You’ll want to register the domain name `networkutopia.com` at a registrar. Registrar is a commercial entity that verifies the uniqueness of the domain name, enters the domain name into the DNS database, and collects a small fee from you for its services. Prior to 1999, a single registrar, Network Solutions, had a monopoly on domain name registration for `com`, `net`, and `org` domains. But now there are many registrars competing for customers. When you register the domain name with some registrar, you also need to provide them the names and IP addresses of your primary and secondary authoritative DNS servers. Suppose the names and IP addresses are `dns1.networkutopia.com`, `dns2.networkutopia.com`, `212.2.212.1`, and `212.212.212.2`. For each of these two authoritative servers, the registrar would then make sure that a Type NS and a Type A record are entered into the TLD com servers. Specifically, for the primary authoritative server for `networkutopia.com`, the registrar would insert the following two resource records into the DNS system: 

```
(networkutopia.com, dns1.networkutopia.com, NS)
(dns1.networkutopia.com, 212.212.212.1, A) 
```

You’ll also have to make sure that the Type A resource record for your Web server `www.networkutopia.com` and the Type MX resource record for your mail server `mail.networkutopia.com` are entered into your authoritative DNS servers. Until recently, the contents of each DNS server were configured statically, for example, from a configuration file created by a system manager. More recently, an UPDATE option has been added to the DNS protocol to allow data to be dynamically added or deleted from the database via DNS messages.

### **Internationalised Domain Names (IDNs)**

IDNs allow domain names to contain non-ASCII characters, such as Arabic, Chinese or letters with diacritics (accents).
Because backend DNS servers still only accept ASCII, the client's web browser automatically translates these special characters into a standard ASCII format using a system called Punycode (which uses generalized variable-length integers). Every translated Punycode domain begins with `xn--`. For example, if a user types `bücher.example`, the browser translates it to `xn--bcher-kva.example` before sending the DNS query over the network.

### DNS Vulnerabilities

The fundamental security flaw of the original DNS architecture is that it is a cleartext protocol with no authentication. Anyone observing the network traffic can read exactly which websites a user is trying to visit. Because there is no authentication, a resolver cannot natively verify if a DNS response actually came from a legitimate authoritative server or an attacker.

- **DDoS bandwidth-flooding attack against DNS servers**

	An attacker could send to each DNS root server a swarm of packets. Such a large-scale DDoS attack took place in 2002. The attackers sent truck loads of ICMP ping messages to each of the 13 DNS root IP addresses. Fortunately, this large scale attack caused minimal damage, having little or no impact on users’ Internet experience since many of the DNS root servers were protected by packet filters, configured to always block all ICMP ping messages directed at the root servers. Furthermore, most local DNS servers cache the IP addresses of top-level-domain servers, allowing the query process to often bypass the DNS root servers. 
	
	A more effective DDoS attack is to send a deluge of DNS queries to TLD servers, for e.g., to servers that handle `.com `domain as TLD servers are not as easily bypassed as are root servers. Such an attack took place against the top-level-domain service provider `Dyn` in 2016. This DDoS attack was accomplished through a large number of DNS lookup requests from botnet consisting of about 100,000 IoT devices that had been infected with **Mirai** malware. For almost a full day, Amazon, Twitter, Netflix, Github and Spotify were disturbed.

- **Homograph Attacks (IDN Spoofing)**

	By abusing IDN support, attackers register malicious domains using characters from foreign scripts that look visually identical to standard Latin letters. For example, an attacker could register `amazon.de` using a Cyrillic "а" instead of a standard Latin "a". To a human user, the URL looks perfectly legitimate, but the underlying Punycode routes them to the attacker's server
	
	![[Screenshot 2026-09-09 at 1.22.27 AM.png]]

- **Man-in-the-Middle (DNS Injection / Spoofing)**
  
	The attacker sits on the network path between the user and the DNS server, observing traffic. When the user queries a domain, the attacker races to inject a fake DNS response before the legitimate server's response can arrive. Because the user's stub resolver usually accepts the first response it receives, it accepts the fake IP and ignores the real answer arriving milliseconds later

- **DNS Cache Poisoning**
  
	Instead of targeting a single user's connection, the attacker targets the ISP's default recursive resolver. The attacker sends unsolicited, bogus replies to the resolver, tricking the server into accepting and caching the fraudulent records. Once the cache is poisoned, the ISP's server will actively distribute the malicious IP address to _all_ users on the network who request that domain 

Either of the above attacks could be used to redirect an unsuspecting Web user to the attacker’s Web site. To combat this, the DNS Security Extensions (DNSSEC) framework (defined in RFC 4033) provides authentication services to protect against these spoofing and poisoning exploits.
