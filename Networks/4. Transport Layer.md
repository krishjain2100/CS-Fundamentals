
**Protocol Data Units (PDU)**:The generic technical term for a single block of data at any specific layer of the network stack. Transport Layer = Segment. Network Layer = Packet
Flow: Application Message $\rightarrow$ Transport **Segment** $\rightarrow$ Network **Packet** $\rightarrow$ Link Frame

### Introduction

**Core Function of the Transport Layer**

- Provides logical communication directly between application processes running on different hosts, making them appear directly connected.

- Implemented exclusively in end systems (hosts), not in network routers.

- Converts application-layer messages into transport-layer packets (called segments) by dividing them into smaller chunks and adding transport-layer headers.

- Passes these segments to the network layer, where they are encapsulated into datagrams (called IP Datagrams in the Internet).


**Transport Layer vs. Network Layer**

- **Network Layer:** Provides logical communication between _hosts_ (devices). The Internet Protocol (IP) offers a best-effort, unreliable delivery service with no guarantees on delivery, order, or data integrity.

- **Transport Layer:** Provides logical communication between _processes_ (applications). It relies on the underlying network layer but can offer services (like reliability or security) that the network layer lacks.

**Key Transport Layer Services**

- **Multiplexing and Demultiplexing:** The fundamental function of extending host-to-host delivery (IP) to process-to-process delivery.

- **Integrity Checking:** Including error-detection fields in headers to ensure data hasn't been corrupted.


**Internet Transport Protocols: UDP vs. TCP**

- **UDP (User Datagram Protocol):**
    - Connectionless and unreliable.
    - Provides only the absolute minimum transport services: multiplexing/demultiplexing and basic error checking.
    - Traffic is completely unregulated. Applications can transmit at any rate they want.

- **TCP (Transmission Control Protocol):**
    - Connection-oriented and reliable.
    - Converts IP's unreliable delivery into a reliable service using flow control, sequence numbers, acknowledgments, and timers.
    - Features congestion control, which regulates the sender's transmission rate to prevent network links and routers from becoming overwhelmed, ensuring a fairer share of bandwidth.


**Core Concepts**

- **Sockets:** Intermediaries (doors) through which data passes between the application process and the network layer.

- **Multiplexing (Sending Host):** Gathering data chunks from multiple sockets, adding transport-layer headers (source and destination ports) to create segments, and passing them down to the network layer.

- **Demultiplexing (Receiving Host):** Examining the header fields of incoming segments to route the data to the correct destination socket.


**Port Numbers**

- 16-bit identifiers ranging from 0 to 65535, used to identify specific sockets.

- **Well-known ports (0–1023):** Strictly reserved for standard protocols (e.g., HTTP uses 80, FTP uses 21).

- **Use of Source Port in transport-layer segment:** Functions as a return address so the receiving host knows where to send its reply. Destination Port is obviously present in transport-layer segment.

**UDP (Connectionless) Demultiplexing**

- A UDP socket is identified strictly by a **two-tuple**: `(Destination IP address, Destination Port number)`.

- If two segments arrive from completely different source IPs or source ports, but share the same destination IP and port, they are routed to the same socket and corresponding processes that handles this socket. This is because two packets from the same source are not related. There is no ordering or anything.


**TCP (Connection-Oriented) Demultiplexing**

- A TCP connection socket is uniquely identified by a **four-tuple**: `(Source IP, Source Port, Destination IP, Destination Port)`.

- If two segments arrive from different source IPs or source ports, they are routed to **different** sockets, even if they share the same destination IP and port (e.g., multiple users connecting to a web server on port 80).

- **Connection Process:** A TCP server uses a single welcoming socket to listen for incoming requests. When a request arrives, the server spawns a brand new, dedicated socket bound specifically to that unique four-tuple to handle the ongoing connection.


**Q. What happens if my code tries to use a port already in use**
The operating system will block the attempt and throw a **`EADDRINUSE` (Address already in use)** error. 

Assume you stop your server (Ctrl+C) and immediately restart it, but it crashes saying the port is in use, even though the server is completely dead. This happens because TCP connections do not close instantly. The OS places the port into a **`TIME_WAIT`** state for 1 to 2 minutes to ensure no delayed, ghost packets from the old connection arrive and corrupt a new connection. You must set the **`SO_REUSEADDR`** socket option _before_ you call `bind()`:

```cpp
int opt = 1;
setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
```


**Security Context: Port Scanning**

- Tools like `nmap` (called port scanners) ping ports sequentially to map out which are open, closed, or unreachable (definitions of these types of ports would be clear later).

- Administrators use this to find which applications are running on hosts of their network as some port numbers are standard for a given application. But attackers use it to identify hosts running specific applications with known security vulnerabilities. E.g., a SQL server listening on port 1434 was subject to a buffer overflow, allowing a remote user to execute arbitrary code on the vulnerable host.

### Firewall

A network firewall locks almost all ports to keep intruders out. To allow employees to browse the internet, the firewall _must_ leave Port 80 (HTTP) and Port 443 (HTTPS) unlocked. If a network administrator blocks these two ports, nobody inside the building can load a website. If malware infects a computer inside this network, it needs to contact the hacker's server to receive instructions or upload stolen data. If the malware tries to sneak out through a random door (like Port 9999), the firewall instantly blocks it because Port 9999 is locked by default. To guarantee its traffic gets out, the malware is programmed to communicate exclusively over Port 80 or 443. It might even format its stolen data to look exactly like standard web traffic. Modern enterprise firewalls can no longer rely on port numbers alone. They now use Deep Packet Inspection (DPI) to examine the actual contents to verify if the traffic on Port 80 is truly a web page, or if it is malware in disguise.

### **Web Servers and TCP Architecture**

- **A Web Server on Port 80:** Every incoming connection request and HTTP message targets the exact same destination (Port 80). The web server completely relies on the TCP 4-tuple (specifically examining the Source IP and Source Port) to untangle the traffic and route it to the correct client socket.

- **Server Concurrency Models:**
    
    - **Process-per-connection (Legacy):** Older web servers spawned a brand new, heavy process for every single client connection.
    
    - **Thread-per-connection (Modern):** High-performance servers typically run a single main process, but spawn lightweight _threads_ for each new connection socket. This means a single process can hold thousands of active sockets simultaneously.

- **The Impact of HTTP Types on Sockets:**
    
    - **Persistent HTTP:** Reuses the exact same TCP connection (and the same socket) to send multiple requests and responses over time. This is highly efficient.
    
    - **Non-persistent HTTP:** Opens and destroys a brand new TCP connection (consequently a new socket) for every single image, script, or page requested. The overhead of constantly creating and tearing down sockets is a severe bottleneck.

### User Datagram Protocol (UDP)

**Core Concepts of UDP**

- **Bare-Bones Protocol:** UDP does almost nothing beyond what the underlying network layer (IP) does. It simply adds multiplexing/demultiplexing (port numbers) and light error checking.

- **Connectionless:** There is no handshake between the sender and receiver. The application simply wraps the data in a UDP segment and blasts it out to the network immediately.

- **One-to-many communication is supported unlike TCP**:

	- **Broadcast:** The server sends a UDP packet to a special broadcast IP address (like `255.255.255.255`). The network switch automatically duplicates this packet and forces every single machine on the local subnet to receive it.
    
	- **Multicast:** The server sends a UDP packet to a specific multicast IP range (e.g., between `224.0.0.0` and `239.255.255.255`). Only clients that have actively subscribed to that specific IP address will receive the packet. The network routers handle the duplication efficiently along the path.


**Why choose UDP over TCP?**

1. **Finer Application Control (No Throttling):** TCP forcefully delays data if the network is congested, and it halts the stream if it needs to retransmit a lost packet. Real-time apps (like VoIP or video games) prefer a dropped packet over a delayed packet. UDP hands full control of the transmission rate to the application.

2. **No Connection Establishment Delay:** Because UDP skips the TCP three-way handshake, it starts transmitting instantly. This is why DNS uses UDP, if a browser had to establish a TCP connection just to look up a website's IP address, web browsing would feel incredibly sluggish.

3. **No Connection State (High Scalability):** TCP must maintain memory buffers, congestion parameters, and sequence numbers for _every single connection_. UDP tracks none of this, allowing a server to handle vastly more simultaneous clients.

4. **Low Overhead:** A UDP header is only 8 bytes, whereas a TCP header is 20 bytes.


**Network Collapse Danger:** Because UDP lacks built-in congestion control, a poorly designed application can blast data at maximum speed regardless of network health. If too many UDP streams do this simultaneously, router queues overflow and packets drop. Worse, TCP connections will start to reduce their speed when they detect this congestion, meaning greedy UDP traffic can easily crowd out TCP traffic.

**Reliability on UDP (The Modern Approach):** Modern protocols like **QUIC** (used by Google Chrome and HTTP/3) use UDP at the transport layer to bypass the OS-level TCP handshake delays, but implement their own custom reliability, ordering, and congestion control directly inside the application layer.

**Security:** When packet loss rates are low, and with some organisations blocking UDP traffic for security reasons, TCP becomes attractivefor streaming media transport. Because UDP is connectionless, it is incredibly easy for hackers to spoof IP addresses or launch massive DDoS attacks using UDP. Because of this, many enterprise firewalls and universities completely block all incoming UDP traffic (except for DNS on port 53)


**UDP Segment Structure**

A UDP segment has 8 bytes of header. The header consists of four fields, each 2 bytes long:

- **Source Port:** Identifies the sender's application (the "return address").
- **Destination Port:** Used for demultiplexing to the correct receiving socket.
- **Length:** The total number of bytes in the segment (Header + Application Data). This is necessary because the payload size changes from packet to packet.
- **Checksum:** Used for basic error detection to ensure data integrity.

If `Length` field cannot store the length of the segment in 16 bits (65535 bytes), the operating system will outright reject it and throw an error.  The IPv4 header contains its own 16-bit length field, which caps the maximum size of an entire IP packet (including all headers and data) at exactly 65,535 bytes. 8-byte UDP header and the 20-byte IPv4 header implies that the maximum payload an application can push into a UDP datagram is 65,535-28 = 65507 bytes.

If you call `sendto()` on a UDP socket with a buffer larger than this limit, the C++ socket API will immediately return `-1` and set the error code to `EMSGSIZE` (Message too long). The packet is never even sent to the network card.

**The UDP Checksum & Error Detection** 

The checksum detects if any bits in the segment were corrupted (flipped) during transit by link noise or hardware glitches.

- **The Sender's Math:** The sender breaks the entire segment into 16-bit words and adds them together. If an addition results in an overflow, the overflow bit is "wrapped around" and added back to the sum. Finally, it takes the **1s complement** of the total (flipping all 0s to 1s, and 1s to 0s) and inserts this into the Checksum field.

- **The Receiver's Math:** The receiver performs the exact same addition of all the 16-bit words, including the checksum field itself. If no errors occurred, the result will be all 1s (`1111111111111111`). If even a single bit is a 0, the receiver knows the packet is corrupted.

- **No Recovery:** UDP only detects errors, it cannot not fix them. A corrupted packet is typically just discarded by the OS, or occasionally passed to the application with a warning.

- In reality, the check-sum is also calculated over a few of the fields in the IP header in addition to the UDP segment like Source IP Address, Destination IP Address, and Protocol Type so that wrongly delivered packets are dropped . But we ignore this detail in order to see the forest through the trees.


**The End-to-End Principle** 

If lower layers like Ethernet already perform error checking on the physical wires, why does UDP need to do it again at the transport layer?

- **No Guarantees:** A packet might cross a dozen different links across the Internet. Not every link-layer protocol guarantees error checking.

- **Router Memory Corruption:** Link-layer error checks only protect the packet while it is physically on the wire. When a packet sits in a router's memory queue waiting to be forwarded, a hardware glitch or cosmic ray can flip a bit.

- **The Principle:** The End-to-End Principle states that because lower levels cannot absolutely guarantee a function (like error-free transit) across the entire path, the highest endpoints (the source and destination hosts) must implement it themselves to be certain. Functions placed at the lower levels may be redundant or of little value. The cost of providing them at the higher level is lesser.

### TCP

**Core Characteristics of a TCP Connection**

- **Connection-Oriented:** Processes must complete a preliminary handshake to initialize state variables and buffers before any application data can be sent.

- **Logical (Not Physical like TDM or FDM):** The connection exists purely as state variables (memory) tracked by the two end systems. The routers sitting between the hosts are oblivious to the connection. They only see individual IP datagrams passing through, which makes sense because TCP protocol runs only on end systems.

- **Full-Duplex:** Application data can flow in both directions (Client to Server, and Server to Client) simultaneously over the exact same connection.

- **Strictly Point-to-Point:** A TCP connection is always between exactly one sender and one receiver. Multicasting (broadcasting from one sender to many receivers) is impossible with TCP.


**Send/Receive Buffers and Data Flow**

- Once the handshake finishes, the operating system allocates a **Send Buffer** and a **Receive Buffer** for each socket (i.e., per connection).

- When your application calls `send()` or `write()`, it simply pushes data through the socke into the socket's send buffer.

- TCP is laid back about transmission: it grabs chunks of data from the Send Buffer and actually transmits them to the network at its own convenience.


**MSS vs. MTU**

- **MTU (Maximum Transmission Unit):** The absolute largest frame the underlying network link (like Ethernet) can carry. For standard Ethernet, the MTU is **1500 bytes**.

- **MSS (Maximum Segment Size):** The maximum amount of _application-layer data_ that can be packed into a single TCP segment.

- MSS is calculated by taking the MTU and subtracting the size of the TCP and IP headers (usually 40 bytes combined). Therefore, standard Ethernet MSS is **1460 bytes**.

- Approaches have been proposed for discovering the path MTU, the largest link-layer frame that can be sent on all links from source to destination, and setting the MSS based on he path MTU value.

### Reliable Data Transfer

The goal of reliable data transfer (RDT) is to guarantee no corrupted bits, no lost packets, and strict in-order delivery over an inherently unreliable channel.

**Core RDT Mechanisms**

- **Checksum:** Detects bit-level errors within a transmitted packet.

- **Acknowledgments (ACK/NAK):** Receiver feedback indicating correct receipt (ACK) or errors (NAK). ACKs can be individual or cumulative.

- **Sequence Numbers:** Sequential numbering that allows the receiver to detect missing gaps (losses) or duplicate packets.

- **Timers:** A countdown mechanism to trigger retransmissions if a packet or its ACK is overly delayed or lost.


**The Evolution of RDT Protocols**

Each version introduces a specific mechanism to address a new type of physical network failure.

**rdt1.0: The Perfect Channel**

- This protocol assumes a completely reliable underlying channel where neither bit errors nor packet loss occur.

- The sender simply creates and sends packets, while the receiver extracts and delivers data without needing to provide any feedback.


**rdt2.0: Handling Bit Errors**

- This version introduces error detection via checksums and receiver feedback using positive (ACK) and negative (NAK) acknowledgments.

- It operates as a stop-and-wait protocol, meaning the sender will not transmit new data until it receives confirmation for the current packet.

- It contains a fatal flaw because if an ACK or NAK is corrupted, the sender cannot know if the receiver successfully got the last transmitted packet.


**rdt2.1: Fixing Corrupted Feedback**

- This version solves the corrupted ACK/NAK problem by adding a 1-bit sequence number (0 or 1) to the data packets.

- If the sender receives a garbled ACK or NAK, it resolves the ambiguity by simply retransmitting the current packet.

- The receiver checks the alternating sequence number to determine if the arriving packet is new data or a duplicate retransmission.


**rdt2.2: A NAK-Free Approach**

- This iteration eliminates explicit NAK packets entirely while maintaining the exact same functionality.

- When the receiver gets a corrupted packet, it sends an ACK for the last correctly received packet and explicitly includes that packet's sequence number.

- If the sender receives two ACKs for the same packet (duplicate ACKs), it treats this exactly like a NAK and retransmits the next packet.


**rdt3.0: Handling Packet Loss**

- This protocol addresses channels that can drop packets entirely by putting the recovery burden on the sender using a countdown timer.

- If the sender does not receive an ACK before the timer expires, it assumes the packet or its ACK was lost and retransmits.

- Because premature timeouts can create duplicate packets, the protocol relies on the alternating 0 and 1 sequence numbers to safely ignore duplicates, earning it the name "alternating-bit protocol".

- While functionally correct, its stop-and-wait nature results in dismal network utilization, which ultimately necessitates the development of pipelined protocols.


**Pipelined Error Recovery**

- **Go-Back-N (GBN):**
    
    - The sender can transmit multiple packets without waiting for an acknowledgment, limited to a sliding window of N unacknowledged packets.
    
    - The receiver uses cumulative acknowledgments, meaning an ACK for packet $n$ confirms that all packets up to and including $n$ were successfully received.
    
    - To radically simplify receiver buffering, the receiver immediately discards any out-of-order packets rather than saving them.
    
    - The sender maintains only a single timer tracking the oldest transmitted but unacknowledged packet.
    
    - If this timer expires, the sender aggressively retransmits all packets that were sent but not yet acknowledged.

- **Selective Repeat (SR):**
    
    - This protocol prevents unnecessary retransmissions by having the sender resend only the specific packets it suspects were lost or corrupted.
    
    - The receiver individually acknowledges each correctly received packet, regardless of whether it arrives in order.
    
    - Out-of-order packets are buffered at the receiver until the missing sequence numbers arrive, allowing them to be delivered to the upper layer in a contiguous batch.
    
    - Because packets are handled independently, the sender must maintain a separate logical timer for every single unacknowledged packet.
    
    - Due to lost ACKs, the sender and receiver windows are often completely out of synchronization.
    
    - To prevent the receiver from confusing a delayed retransmission with a brand-new packet after sequence numbers wrap around, the window size must be less than or equal to half the total sequence number space.


**Packet Reordering Hazard: Maximum Segment Lifetime:** 

In real networks, old packets can be delayed in routers and spontaneously emerge later. To prevent these delayed packets from arriving after a sequence number wraps around and being mistaken for new data, protocols enforce a maximum packet lifetime (e.g., 3 minutes) to ensure old copies die before a sequence number is reused.

### TCP Segment Structure

![[Screenshot 2026-09-11 at 2.43.54 AM.png]]

Unlike UDP’s tiny 8-byte header, TCP requires at least 20 bytes to manage its state. 

- **Source & Destination Ports (16 bits each):** Identifies the application endpoints for multiplexing and demultiplexing.
- **Sequence Number (32 bits):** The byte-stream index of the first data byte contained in this segment.
- **Acknowledgment Number (32 bits):** The sequence number of the _next_ byte the receiver expects to get, providing cumulative acknowledgment.
- **Receive Window (16 bits):** Drives TCP flow control. It tells the amount of free space remaining in the receiver's buffer.
- **Header Length (4 bits):** Specifies the total size of the TCP header in 32-bit words. This is mandatory because the Options field makes the total header length variable.
- **Internet Checksum (16 bits):** Detects bit-level corruption across the header and payload.
- **Options (Variable):** Used during the initial handshake to negotiate advanced parameters, such as the Maximum Segment Size (MSS), time-stamping, or window scaling for high-speed links.


**TCP Control Flags (The 6-bit Field)**

| **Flag**      | **Name**       | **Purpose**                                                                                                                                                                                             |
| ------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SYN**       | Synchronize    | Initiates a new connection. Used exclusively in the first two steps of the 3-way handshake.                                                                                                             |
| **FIN**       | Finish         | Gracefully closes the connection, indicating the sender has no more data to transmit.                                                                                                                   |
| **RST**       | Reset          | Abruptly aborts the connection. Often triggered when a packet hits a closed port or a host crashes.                                                                                                     |
| **ACK**       | Acknowledgment | Validates that the Acknowledgment Number field contains legitimate data. Set on almost every packet after the initial SYN.                                                                              |
| **PSH**       | Push           | Instructs the receiving OS to immediately flush the data to the application layer (like a C++ server) instead of waiting for the receive buffer to fill up. (Rarely used today)                         |
| **URG**       | Urgent         | If on, **Urgent Data Pointer** points to last byte of portion that needs immediate processing, bypassing the normal stream order. Urgent data starts at first position is implicit. (Rarely used today) |
| **CWR & ECE** | Congestion     | Explicit Congestion Notification (ECN) flags used to signal network bottlenecks before packet loss actually occurs.                                                                                     |

**Byte-Stream Paradigm**

TCP does not think in messages or packets. It views data as one continuous river of bytes.

- **Sequence Number:** It is the byte-offset. If your MSS is 1,000 bytes, the first segment's sequence number is `0`, the second is `1000`, and the third is `2000`.
- **Acknowledgment Number (ACK):** This is the sequence number of the **next byte** the receiver expects. It is TCP's way of saying, "I have successfully received every single byte up to X-1, please send me byte X."


**Why TCP Counts Bytes Instead of Segments**

- **Dynamic Repacketisation:** If the network's Maximum Transmission Unit (MTU) suddenly shrinks, a lost 1,400-byte packet cannot be retransmitted whole. Byte counting allows the OS to seamlessly chop the retransmission into smaller chunks (e.g., bytes 0–999 and 1000–1399) without breaking the protocol.

- **Packet Coalescing:** If your application makes multiple tiny `send()` calls, the OS can merge them into a single efficient network packet. Segment counting would lock each `send()` into its own rigid packet, severely multiplying header overhead.

- **Direct Memory Mapping:** The OS receive buffer is a flat array in RAM. The byte sequence number acts as a direct memory pointer (`base_address + seq_num`), allowing the kernel to copy the payload directly into place. Segment numbers would require more implementation.


**Cumulative Acknowledgments & Out-of-Order Delivery** 

Because TCP uses cumulative ACKs, it can handle dropped packets elegantly. Assume the server receives bytes `0-500`, loses `501-1000`, but receives `1001-1500`. It will stubbornly send back an ACK of `501`. It refuses to acknowledge the newer data until the missing gap is filled. 


**What does a host do when it receives out-of-order segments in a TCP connection?**

Interestingly, the TCP RFCs do not impose any rules here and leave the decision up to the programmers implementing a TCP implementation. There are two choices: 

- the receiver immediately discards out-of-order segments (simplifies receiver design)
- the receiver keeps the out-of-order bytes and waits for the missing bytes to fill in the gaps. 

Clearly, the latter choice is more efficient in terms of network bandwidth, and is the approach taken in practice.

**ISN Randomization (Initial Sequence Number)**

TCP does not start counting byte sequence numbers from `0`. During the 3-way handshake, both the client and server independently generate a random 32-bit starting number. If a ghost packet arrives during a new session, its old sequence number will fall wildly outside the new connection's randomized sequence window. The operating system instantly recognizes this and silently drops the packet.

### Case Study for Sequence and Acknowledgment Numbers

This Telnet case study perfectly illustrates how TCP manages sequence and acknowledgment math in a interactive, character-by-character environment.

**Telnet Protocol Context**

- **Design:** An interactive, application-layer remote login protocol running over TCP.
- **The Echo-Back Mechanism:** Every typed character traverses the network twice (client to server, then echoed back from server to client) to visually confirm it was received and processed.

**The Scenario: Typing a single letter ('C')**
- **Payload:** 1 byte (the ASCII character 'C').
- **Client Initial Sequence Number (ISN):** 42
- **Server Initial Sequence Number (ISN):** 79

**The 3-Step Exchange**

| Step                  | Direction       | Seq # | ACK # | Data      | Purpose                                                                                                     |
| --------------------- | --------------- | ----- | ----- | --------- | ----------------------------------------------------------------------------------------------------------- |
| **1. The Keystroke**  | Client ➔ Server | 42    | 79    | `'C'`     | Client sends its byte 42. It expects the server's byte 79 next.                                             |
| **2. The Echo & ACK** | Server ➔ Client | 79    | 43    | `'C'`     | Server sends its byte 79. It acknowledges receiving client's byte 42 by asking for byte 43 (`42 + 1 = 43`). |
| **3. The Final ACK**  | Client ➔ Server | 43    | 80    | _(Empty)_ | Client acknowledges receiving the server's byte 79 by asking for byte 80 (`79 + 1 = 80`).                   |

**Key TCP Concepts Demonstrated**

- **Piggybacking:** Instead of sending an empty ACK packet and then a separate packet containing the echoed 'C', the server combines them. It piggybacks the Acknowledgment onto the outgoing application data.

- **Mandatory Sequence Numbers:** Even though the final client acknowledgment contains zero bytes of application data, it is still strictly assigned a Sequence Number (43) because the TCP header architecture demands it. The next packet, is user pressed 'D' would also have Sequence Number 43.

### TCP Timeout and RTT Estimation

The OS kernel completely abstracts packet loss, jitter, and duplicate deliver, the application's `recv()` call always receives a clean, in-order byte stream.

The critical challenge is determining exactly how long the timer of retransmit should be. If the timer is too short, the server wastes bandwidth retransmitting packets that were just slightly delayed. If the timer is too long, the application freezes waiting for lost data. To solve this, TCP constantly calculates a dynamic timeout interval using three steps:

**1. SampleRTT (The Raw Measurement)** 

TCP records the exact time it pushes a segment onto the wire and measures how many milliseconds it takes for that specific segment's ACK to return. This can be done by putting the Created Timestamp in the options field which is echoed back by the receiver in the ACK. Also note that TCP never calculates a `SampleRTT` for a packet that had to be retransmitted. If a packet is sent twice, TCP cannot know if the ACK it just received belongs to the first (delayed) copy or the second copy. 

**2. EstimatedRTT (The Smoothed Average)** 

Because network congestion causes `SampleRTT` to fluctuate wildly, TCP smooths the data using an Exponential Weighted Moving Average (EWMA).
**Formula:** `EstimatedRTT = 0.875 * EstimatedRTT + 0.125 * SampleRTT`
By giving the historical average an 87.5% weight and the new sample only a 12.5% weight, TCP ignores sudden, temporary latency spikes, but slowly adapts if the network genuinely becomes slower over time. (1/8 weightage to new value is recommended in RFC)

**3. DevRTT (The Variance)** 

TCP also calculates how wildly the ping is fluctuating.
**Formula:** `DevRTT = 0.75 * DevRTT + 0.25 * abs(SampleRTT - EstimatedRTT)`
(1/4 weightage to new value is recommended in RFC).

**The Final Timeout Calculation** 

TCP takes the smoothed average and adds a safety margin equal to four times the current network variance.  **Formula:** `TimeoutInterval = EstimatedRTT + 4 * DevRTT`

An initial TimeoutInterval value of 1 second is recommended. Also, when a timeout occurs, the value of TimeoutInterval is doubled. However, as soon as a segment is received and EstimatedRTT is updated, the TimeoutInterval is again computed using the formula above.

### TCP Reliable Data Transfer & Pipelining

- **Timers & Positive ACKs:** TCP relies on countdown timers and positive acknowledgments to guarantee delivery. Because TCP cannot distinguish between a segment that was lost, corrupted, or simply delayed, its universal response to a missing ACK is to retransmit the segment.

- **Fast Retransmit (Implicit NAKs):** TCP does not use explicit negative acknowledgments. Instead, receiving **three duplicate ACKs** (in addition to the original ACK) for the exact same segment serves as an implicit NAK. This triggers an immediate retransmission of the missing data long before the countdown timer actually expires.

- **Pipelining for Throughput:** To maximize network efficiency (especially when the round-trip time is large), TCP pipelining allows the sender to keep multiple unacknowledged segments in flight simultaneously rather than stopping and waiting for each individual ACK.

- **Dynamic Window Limits:** The specific number of unacknowledged segments allowed in the pipeline at any given moment is strictly governed by TCP's flow-control (protecting the receiver) and congestion-control (protecting the network routers) mechanisms.

### **The TCP Sender: 3 Core Events**

There is a massive CPU overhead of tracking thousands of individual timers. So TCP uses a  optimized hybrid approach: it relies on **cumulative ACKs** and a **single retransmission timer** tracking only the oldest unacknowledged segment.

**State Variables**
- **SendBase:** The sequence number of the oldest transmitted but unacknowledged byte.
- **NextSeqNum:** The sequence number that will be assigned to the next new byte of data passed down from the application.

**1. Data Received from the Application**

- When your application calls `send()`, TCP encapsulates the data and assigns a sequence number based on the byte-offset.

- **Timer Logic:** TCP checks if the timer is already running. If it is not, it starts the timer for this segment. The timer effectively acts as a stopwatch for the oldest unacknowledged byte in the pipeline.

- TCP then passes the segment down to the IP layer and updates its internal `NextSeqNum` variable to prepare for the next application write.


**2. Timeout Expires**

- If the `TimeoutInterval`(calculated via  `EstimatedRTT + 4 * DevRTT` formula) expires before an ACK arrives, TCP assumes the network dropped the packet.

- **The Reaction:** TCP retransmits **only** the oldest unacknowledged segment that caused the timeout (the one at `SendBase`).

- It immediately restarts the timer to give this newly retransmitted segment a fresh countdown.


**3. Acknowledgment (ACK) Arrives**

- **Window Sliding:** The sender compares incoming ACK `y` to its `SendBase` (the sequence number of the oldest unacknowledged byte). If `y > SendBase`, it means new data was successfully received. The sender sets `SendBase` forward to `y`.

- **Timer Reset:** If sliding the window clears out all in-flight data, the timer is stopped. If there are still unacknowledged segments waiting in the pipeline, the timer is restarted.


**Example:**
Host A sends two segments back to back. The first segment has sequence number 92 and 8 bytes of data, and the second segment has sequence number 100 and 20 bytes of data. Suppose that both segments arrive intact at B, and B sends two separate acknowledgments for each of these segments. The first of these acknowledgments has ack number 100, the second has ack number 120. Suppose now that neither of the acknowledgments arrives at Host A before the timeout. When the timeout event occurs, Host A resends the first segment with sequence number 92 and restarts the timer. As long as the ACK for the second segment arrives before the new timeout, the second segment will not be retransmitted.


**Exponential Backoff and Fast Retransmit**

- A timeout usually implies a router on the network path is overwhelmed and actively dropping packets. If TCP aggressively fired off retransmissions using the standard `TimeoutInterval`, it would flood the router further and make the congestion worse.

-  So when a timeout occurs, TCP completely ignores the `EstimatedRTT` formula and sets the new timeout interval to twice the previous value. If the retransmission also times out, the interval doubles again.

- The dynamic RTT-based formula is only restored when a timer is cleanly triggered by new application data or a successful ACK.

- Waiting for an exponentially backed-off timer to expire creates massive latency. The sender needs a way to detect a dropped packet before the clock runs out. So we have the three duplicate ACK rule.


**Delayed ACKs**

The ACK to be sent by the receiver is usually delayed by 500ms.

- It waits for the application to generate a response (like an HTTP reply), allowing the OS to piggyback the ACK onto the outgoing application data.

- The pause provides time for a second incoming segment to arrive, allowing the receiver to confirm both segments simultaneously with a single cumulative ACK.

### Go-Back-N or Selective Repeat?

TCP’s error-recovery mechanism functions as a hybrid of both Go-Back-N (GBN) and Selective Repeat (SR) protocols, combining the lightweight state tracking of GBN with the efficient retransmission behavior of SR.

**Similarities with Go-Back-N**

- **Cumulative Acknowledgments**
- **Minimal Sender State:** The TCP sender only needs to track two main sequence numbers: the oldest unacknowledged byte (`SendBase`) and the next byte to be sent (`NextSeqNum`).


**Similarities with Selective Repeat**

- **Out-of-Order Buffering**
- **Efficient Retransmission:** If a sender transmits segments 1 through N and the ACK for segment _n_ is lost, strict GBN would retransmit _n_ and all subsequent packets upon timeout. TCP will retransmit at most one segment (_n_). Furthermore, if the cumulative ACK for segment _n+1_ arrives before _n_'s timeout, TCP will not retransmit anything.


**The Proposed SACK Extension** 

The Selective Acknowledgment (SACK) modification bridges the final gap between TCP and strict SR. By enabling the receiver to explicitly list the out-of-order blocks it has successfully buffered, the sender can selectively retransmit only the missing segments rather than falling back on purely cumulative ACK rules.

### Flow Control

TCP Flow Control is a speed-matching service designed to prevent a fast sender from overflowing a slower receiver's local memory buffer.

**Flow Control vs. Congestion Control**
- **Flow Control:** Protects the _end receiver's_ application buffer.
- **Congestion Control:** Protects the _intermediate network_ (IP router queues) from being overwhelmed. Though both throttle the sender, their triggers and purposes are entirely different.

**The Mechanics: The Receive Window (`rwnd`)**

- **The Receiver's Buffer:** The receiving OS allocates a specific buffer size ($RcvBuffer$) for the connection. The application reads from this buffer at its own unpredictable pace.

- **Calculating Spare Room:**  $rwnd = RcvBuffer - (LastByteRcvd - LastByteRead)$

- **Advertising:** The receiver continuously broadcasts this dynamic $rwnd$ value back to the sender by embedding it in the Receive Window field of the TCP header.

- To guarantee it never overflows the receiver, the sender tracks its in-flight data (bytes sent but not yet ACKed) and strictly enforces: $(LastByteSent - LastByteAcked) \le rwnd$


**The Zero-Window Deadlock & The 1-Byte Fix**

- **The Trap:** If the application stalls, the buffer fills up, and the receiver advertises $rwnd = 0$. The sender dutifully stops transmitting. Later, the application finally reads the data, opening up space. However, because TCP only generates packets to send data or ACKs, the receiver has no spontaneous way to tell the sender that the window is open again. The connection is deadlocked.

- **The Fix:** To prevent permanent freezing, the TCP specification requires the sender to periodically transmit a 1-byte (41 bytes includign headers) probe segment when $rwnd = 0$. This forces the receiver to respond with an ACK containing the newly updated, non-zero $rwnd$ value, safely unpausing the data flow.

### TCP Connection Management

TCP connection management governs how connections are established, maintained, and torn down, ensuring both hosts allocate and release resources symmetrically.

**TCP Connection Establishment (The 3-Way Handshake)**

- **Step 1 (SYN):** The client sends a segment with the SYN flag set to 1, containing no payload, and selects a random Initial Sequence Number (`client_isn`).

- **Step 2 (SYNACK):** The server receives the SYN, allocates TCP buffers and variables (doing it later is modern and safer), and responds with a segment where SYN is 1. It acknowledges the client's sequence by setting the ACK field to `client_isn + 1` and provides its own random `server_isn`.

- **Step 3 (ACK):** The client receives the SYNACK, allocates its own buffers and variables, and acknowledges the server by sending a segment with SYN set to 0 and the ACK field set to `server_isn + 1`. This final step can carry the first application payload. If the client does not send an ACK to complete the third step of this 3-way handshake, eventually (often after a minute or more) the server will terminate the half-open connection and reclaim the allocated resources

**Why a 3-way handshake instead of 2-way?**

A 2-way handshake only confirms the client-to-server path. If the process stopped here, the server has absolutely no idea if its SYNACK ever reached the client. It doesn't know if the client's receiver actually works. Because TCP is full-duplex, the server also needs explicit confirmation that the client is alive and ready to receive data. More importantly, it prevents delayed, duplicate connection requests from the past from tricking the server into opening a dead connection that the client no longer wants.

**Why randomize Initial Sequence Numbers (ISNs)?** 

If ISNs always started at 0, an attacker could easily guess the sequence numbers and inject malicious packets into an active stream (TCP hijacking). Randomization also prevents ghost packets from an old, terminated connection from accidentally matching the sequence numbers of a brand-new connection on the same port.


**TCP Connection Teardown**

![[Screenshot 2026-09-11 at 10.14.54 PM.png]]

**Active Close States (Typically the Client)** 
The side that decides to terminate the connection carries the burden of the `TIME_WAIT` failsafe.

- **FIN_WAIT_1:** The application calls close(). The TCP stack sends a `FIN` segment and waits for an acknowledgment.

- **FIN_WAIT_2:** The `ACK` for the `FIN` is received. The client is now waiting for the server to finish its own transmissions and send a `FIN`.

- **TIME_WAIT:** The server's `FIN` is received, and the client sends its final `ACK`. The client enters a timed holding pattern (typically 30 seconds to 2 minutes) to catch any retransmitted `FIN`s.

- **CLOSED:** The timer expires, and the client finally deallocates its ports and buffers.


**Passive Close States (Typically the Server)** 

- **CLOSE_WAIT:** The server receives the client's `FIN` and replies with an `ACK`. The server's TCP stack tells the local application that the client wants to shut down. The connection is now half-closed (the client is done sending, but the server can still send data if needed).

- **LAST_ACK:** The server application finishes its work and tells its TCP stack to close. The server sends its own `FIN` and waits for the final confirmation.

- **CLOSED:** The moment the server receives the client's final `ACK`, it  deallocates all connection variables and buffers, and formally closes.

The `TIME_WAIT` state lets the TCP client resend the final ack in case the ACK is lost.
- **The Server's Timer:** When the server sends its final `FIN` segment, it starts a standard retransmission countdown timer. It is actively waiting for the client's final `ACK`.
- **The Dropped ACK:** The client sends the final `ACK` and enters `TIME_WAIT`. If that `ACK` drops on the network, the server's timer eventually expires.
- **The Server Retransmits:** Because its timer expired, the server assumes its `FIN` never made it to the client. The server retransmits the `FIN` segment.
- **The Client's Trigger:** The client is sitting in the `TIME_WAIT` state specifically listening for this potential duplicate `FIN`. When the duplicate `FIN` arrives, it acts as the signal that the original `ACK` was lost. The client dutifully resends the `ACK` and restarts its `TIME_WAIT` clock.

### RST Packet

The TCP Reset (RST) packet is a segment with the RST control flag set to 1, functioning as an emergency kill switch to abruptly abort a connection.

**Common Triggers for an RST Packet**

- **Closed Ports:** If a host receives a segment for a port with no listening application, it fires an RST to tell the sender to stop transmitting.

- **State Confusion:** If a host receives a packet for a connection it believes is already closed (such as a delayed ghost packet), it sends an RST to correct the sender's state.

- **Intentional Abort:** An application or firewall can instruct the operating system to forcefully drop a connection if it detects a severe timeout, crash, or malicious behavior.

**The Mechanics of Ungraceful Termination**

- **Bypassing the Handshake:** A graceful shutdown uses the `FIN` exchange. An RST completely bypasses this sequence, instantly tearing down the connection without waiting for any acknowledgments.

- **Immediate Data Destruction:** The moment an OS receives or sends an RST, it instantly flushes and destroys the socket's memory buffers. Any unread data sitting in the receive buffer, or data currently in flight on the network, is permanently deleted. The OS makes zero attempt to recover or deliver it.

- **Application-Level Shock:** Because the teardown bypasses standard protocol, the receiving application process does not get a clean signal. Instead, the process's `read()` or `recv()` system call is violently interrupted, throwing a fatal socket exception (typically `ECONNRESET` or "Connection reset by peer"). If the application is not programmed to catch and handle this specific exception, the process will instantly crash. For handling, you need to call `close(sockfd)` to deallocate local memory for the socket and reuse the FD number or else that memory would be permanently trapped (memory leak).

### Nmap

To explore a specific TCP port, say port 6789, on a target host, nmap will send a TCP SYN segment with destination port 6789 to that host. There are three possible outcomes:

1. The source host receives a TCP SYNACK segment from the target host. Since this means that an application is running with TCP port 6789 on the target post, nmap returns “open.”
2. The source host receives a TCP RST segment from the target host. This means that the SYN segment reached the target host, but the target host is not running an application with TCP port 6789. But the attacker at least knows that the segments destined to the host at port 6789 are not blocked by any firewall on the path between source and target hosts.
3. The source receives nothing. This likely means that the SYN segment was blocked by an intervening firewall and never reached the target host.

Nmap is a powerful tool not only for open TCP ports, but also for open UDP ports, for firewalls and their configurations, and even for the versions of applications and operating systems. Most of this is done by manipulating TCP connection-management.

### **SYN Flood Attacks & SYN Cookies**

- **The Vulnerability:** A SYN flood is a Denial of Service (DoS) attack where an attacker spams Step 1 (SYN) but never completes Step 3. The server allocates memory for thousands of half-open connections until it crashes or denies legitimate users.

- **The Defense (SYN Cookies):** When the server receives a SYN, it does _not_ immediately allocate memory. Instead, it generates a hash based on the IP addresses, ports, and a secret server key. It sends this hash back as its `server_isn` (the cookie). The server then forgets the interaction entirely. If a legitimate client completes Step 3, they return the cookie + 1. The server re-calculates the hash, verifies the cookie, and _only then_ allocates the memory buffers.

### Congestion Control

Network congestion occurs when too many sources attempt to send data at too high a rate, and congestion control is the mechanism used to throttle these senders to treat the root cause.

**The Three Costs of Network Congestion**

- **Infinite Queuing Delays:** In a scenario with infinite router buffers, as the packet arrival rate nears the link's maximum capacity (R), throughput maxes out but the average queuing delay becomes infinite.

- **Bandwidth Wasted on Retransmissions:** In realistic networks with finite buffers, routers will drop packets when full. The sender must perform retransmissions to compensate, which means a portion of the link's capacity is consumed by duplicate data rather than new payloads. Furthermore, premature timeouts cause routers to waste bandwidth forwarding completely unneeded copies of packets.

- **Upstream Capacity Waste:** In multi-hop paths, if a packet successfully traverses several routers only to be dropped at a downstream router due to congestion, the transmission capacity used by every upstream link to move that packet is completely wasted. In extremely heavy traffic, this cascading waste drives end-to-end throughput to zero.


**Approaches to Congestion Control**

- **End-to-End Congestion Control:** The network layer provides no explicit support or feedback to the transport layer. End systems must deduce the presence of congestion strictly from observed network behavior, such as segment loss or increasing delays. TCP utilizes this approach, interpreting timeouts or the receipt of three duplicate acknowledgments as congestion indicators, and decreases its window size accordingly.

- **Network-Assisted Congestion Control:** Routers actively provide explicit feedback to the sender or receiver about the network's congestion state.  This feedback may be as simple as a single bit indicating congestion at a link/router. More sophisticated feedback is also possible. For example, in **ATM Available Bite Rate (ABR)** congestion control, a router informs the sender of the maximum host sending rate it (the router) can support on an outgoing link. 

The Internet-default versions of IP and TCP adopt an end-to-end approach towards congestion control. We’ll see that IP and TCP may also optionally implement network-assisted congestion control.

Network Assisted Congestion Control is implemented in two ways:
- **Direct Notification:** A congested router sends a direct "choke packet" back to the sender.
- **Packet Marking:** A router updates a specific field in a data packet as it flows toward the receiver. Upon getting this marked packet, the receiver is responsible for notifying the sender of the congestion.

### TCP Congestion Control

**The Congestion Window (`cwnd`)**

- While the Receive Window (`rwnd`) prevents overwhelming the receiver's memory, the Congestion Window (`cwnd`) prevents overwhelming the intermediate network routers.

- The sender strictly limits its unacknowledged data in flight using the following constraint: 
	$LastByteSent - LastByteAcked \le \min(cwnd, rwnd)$

- Assuming a large receiver buffer, the sender's transmission rate is roughly defined as $cwnd / RTT$ bytes per second.

**Detecting Congestion**

TCP senders are not explicitly coordinated by network routers. They operate via a distributed approach, independently deducing network state using implicit local signals:

- **Loss Events (Congestion):** The occurrence of a timeout or the receipt of three duplicate ACKs implies a router buffer has overflowed. The sender must actively decrease its rate.

- **Self-Clocking (Clear Path):** The arrival of clean ACKs indicates successful delivery. TCP uses the rate of returning ACKs to "clock" or naturally trigger its window increases, scaling up faster on low-latency connections.


**The 3-Phase Congestion Control Algorithm**

**1. Slow Start (Exponential Growth)**

- **The Ramp Up:** The connection begins with $cwnd = 1$ MSS (Maximum Segment Size). For every ACK received, $cwnd$ increases by 1 MSS. Because an entire window of ACKs returns per RTT, the sending rate effectively _doubles_ every RTT. You have to be careful about the fact that some ACKs my be clubbed, so some byte counting algorithm has to be applied to get actually get to double the original value.

- **The Exit Triggers:** Exponential growth stops and transitions to linear Congestion Avoidance if $cwnd$ hits the Slow Start Threshold (`ssthresh`). If a timeout occurs, $cwnd$ hard-resets to 1 MSS, and `ssthresh` drops to half of the $cwnd$ value at the time of the crash. Initially $ssthresh$ is not set (infinite).


**2. Congestion Avoidance (Linear Growth)**

- Once $cwnd \ge ssthresh$, TCP assumes it is nearing the network's maximum capacity.
- It abandons exponential growth for a conservative, linear increase, adding exactly 1 MSS to the total window size per RTT. This can be accomplished in several ways. A common approach is for the TCP sender to increase $cwnd$ by $MSS * (MSS/cwnd)$ bytes when ever a new acknowledgment arrives. For example, if $MSS$ is 1,460 bytes and $cwnd$ is 14,600 bytes, then 10 segments are being sent within an RTT. Each arriving ACK (assuming one ACK per segment) increases the congestion window size by 1/10 of MSS, and thus, the value of the congestion window will have increased by one MSS after ACKs when all 10 segments have been received.


**3. Fast Recovery (Handling 3 Dup ACKs)**
Fast recovery is a recommended, but not required, component of TCP.

- **TCP Tahoe (Legacy):** Treats all loss identically.  Sets $ssthresh$ to $cwnd/2$ and cuts $cwnd$ to 1 MSS and restarts Slow Start.
- **TCP Reno (Modern):** Recognizes that 3 duplicate ACKs mean the network is still partially functioning and delivering out-of-order packets. It sets `ssthresh` to $cwnd / 2$, cuts $cwnd$ in half (plus 3 MSS for the duplicate ACKs), and enters Fast Recovery. It temporarily increases $cwnd$ by 1 MSS for every subsequent duplicate ACK (for the missing segment that caused TCP to enter fast-recovery state) until the missing packet is explicitly acknowledged, at which point it drops back into Congestion Avoidance by bringing $cwnd$ back to $ssthresh$ and continuing linear growth.  
  If the retransmitted packet is also dropped and the actual countdown timer expires while sitting in Fast Recovery, TCP realises the network is genuinely crippled. It aborts the recovery effortd, sets $ssthresh$ to $cwnd/2$ and drops `cwnd` to 1 MSS, and falls back to Slow Start.

TCP congestion control fundamentally operates as an **Additive-Increase, Multiplicative-Decrease (AIMD)** algorithm, balancing aggressive bandwidth probing with cautious recovery.

- **Additive Increase:** While in the Congestion Avoidance phase, TCP continuously probes for available network capacity by linearly adding exactly 1 MSS to the congestion window for every Round Trip Time (RTT).
- **Multiplicative Decrease:** The moment congestion is detected via three duplicate ACKs, TCP instantly cuts the congestion window in half to rapidly relieve pressure on the network's routers.

Because the congestion window climbs gradually but drops sharply, graphing the transmission rate over time produces a distinct saw-tooth wave. This represents pushing the network to its absolute limit, backing off exactly when packets start dropping, and immediately beginning to push again.

![[Screenshot 2026-09-12 at 12.54.28 AM.png]]

A simplified mathematical model to estimate the average speed of a long-lived TCP Reno:

- Because the exponential growth phase is so brief, this model assumes the connection spends almost all its time strictly in the linear Congestion Avoidance phase.
- It assumes both the Round Trip Time ($RTT$) and the maximum congestion window size just before a packet drop ($W$) remain perfectly constant over time.
- Right before a packet drops, the sender is pushing data at its absolute limit. The transmission rate at this exact moment is $\frac{W}{RTT}$.
- The moment the loss occurs, the transmission rate instantly drops to $\frac{W}{2 \cdot RTT}$.
- Because the window linearly between the valley and the peak, the average speed is halfway between the minimum and the maximum. Therefore, the macroscopic average throughput of the entire connection is **$0.75 \cdot \frac{W}{RTT}$**.

### TCP Splitting

- **The Slow Start Penalty:** For distant clients, the Round Trip Time (RTT) to a centralized Data Center is large. Delivering a standard dynamic response (like a search query) typically requires three TCP windows to complete during the Slow Start phase.

- **Standard TCP Math:** The total baseline delay without optimization is $4 \cdot RTT + \text{processing time}$. This accounts for 1 RTT to complete the initial TCP setup handshake, plus 3 RTTs to transmit the three windows of data.

- **The TCP Splitting Solution:** Cloud providers (like Google or Akamai) deploy Front-End (FE) servers close to users. The client establishes its TCP connection strictly with the nearby FE server. The FE server then forwards the request to the Back-End (BE) Data Center over a pre-warmed, persistent TCP connection that already possesses a massively inflated congestion window (`cwnd`).

- **Optimized TCP Math:** The new response time calculation becomes $4 \cdot RTT_{FE} + RTT_{BE} + \text{processing time}$.

- **The Net Performance Gain:** Because the Edge server is physically close to the user, $RTT_{FE}$ is negligibly small. Meanwhile, the transit time between the FE and the Data Center ($RTT_{BE}$) is roughly equal to the original end-to-end $RTT$. By bypassing Slow Start on the long-haul link, TCP splitting slashes the total networking delay from approximately $4 \cdot RTT$ down to approximately $1 \cdot RTT$.

- **Packet Loss Mitigation:** This architecture isolates unreliable access networks. If a packet drops on the "last mile" to the user's device, the retransmission is handled entirely by the nearby FE server using the tiny $RTT_{FE}$, preventing a massive latency penalty.

### TCP CUBIC

TCP Reno’s linear additive increase is highly cautious. When a loss occurs, Reno cuts its speed in half and slowly crawls back up one segment at a time. If the network's capacity hasn't actually changed, this slow crawl leaves available bandwidth unused for a long period.

TCP CUBIC (the default congestion control in Linux) modifies _only_ the Congestion Avoidance phase. Its core philosophy is to sprint back to the known safe speed, tiptoe around the danger zone, and then sprint again if the coast is clear.

Instead of a straight line, CUBIC grows the congestion window along a cubic curve based on the time elapsed since the last packet loss. It uses three key variables:

- $W_{max}$: The size of the congestion window when the last packet loss occurred (the known danger point).
- $K$: A calculated future timestamp when the window is projected to reach $W_{max}$ again, assuming no losses. Several tunable CUBIC parameters determine this value.
- $t$: The current time.

**The Three Stages of the Cubic Curve**

By calculating growth as a function of the cube of the distance between $t$ and $K$, the curve naturally creates three distinct growth behaviors:

1. **Fast Ramp-Up ($t$ is far below $K$):** Immediately after a loss, the curve is steep. CUBIC aggressively inflates the window to quickly recover the throughput that was just lost.

2. **Cautious Probing ($t$ approaches $K$):** As the window gets very close to the old $W_{max}$, the curve flattens out. CUBIC almost pauses its growth, carefully tiptoeing just below the known congestion threshold to maintain high throughput without triggering another loss.

3. **Accelerated Discovery ($t$ exceeds $K$):** If the window surpasses $W_{max}$ without any packet loss, CUBIC assumes the network's congestion has cleared up. The curve steepens again, growing rapidly to hunt for the new, higher network limit.

Because CUBIC spends much more time hovering right at the maximum capacity rather than slowly crawling toward it, it achieves significantly higher overall throughput than Reno.

### Network-Assisted Explicit Congestion Notification and  Delayed-based Congestion Control

Explicit Congestion Notification (ECN) and delay-based algorithms offer proactive alternatives to TCP Reno's reactive, loss-driven approach. Instead of waiting for a router buffer to overflow and drop a packet, these mechanisms attempt to detect and mitigate congestion before a drop ever occurs.

#### Explicit Congestion Notification (ECN)

- **The Network Layer (IP):** Before its buffers completely fill, a congested router modifies an IP datagram passing through it by setting specific ECN bits in the IP header.
- **The Receiver (TCP):** Upon receiving this flagged IP datagram, the destination host extracts the warning and sets the ECN-Echo (ECE) bit in its next TCP ACK segment back to the sender.
- **The Sender (TCP):** Seeing the ECE bit, the sender proactively halves its congestion window (`cwnd`) just as it would for a fast retransmit. It then sets the Congestion Window Reduced (CWR) bit in its next outgoing segment to confirm to the receiver that it has throttled its rate.

#### Delay-Based Congestion Control (TCP Vegas & BBR)

Rather than relying on explicit router flags or packet drops, delay-based algorithms use mathematical measurements of latency to deduce network state.

- **TCP Vegas:** The sender constantly tracks `RTTmin` to calculate its theoretical maximum uncongested throughput ($\frac{cwnd}{RTTmin}$). If the actual, measured throughput falls significantly below this theoretical calculation, it proves that packets are actively sitting in router queues. Vegas immediately reduces the sending rate to prevent those queues from overflowing.

- **Modern Evolution:** TCP BBR (Bottleneck Bandwidth and Round-trip propagation time) builds heavily on these latency-measurement concepts. It has largely replaced TCP CUBIC across Google's internal networks and YouTube servers to provide high throughput with minimal queuing delay.

### Fairness

Consider  $K$ TCP connections share a bottleneck link of capacity $R$. Suppose each connection is transferring a large file and there is no UDP traffic passing through the bottleneck link. A congestion-control mechanism is said to be fair if the average transmission rate of each connection is approximately $R/K$.

**AIMD Convergence**

Assume that the two connections have the same MSS and RTT (so that if they have the same congestion window size, then they have the same throughput), that they have a large amount of data to send, and that no other TCP connections or UDP datagrams traverse this shared link. Also, ignore the slow-start phase of TCP and assume the TCP connections are operating in CA mode (AIMD) at all times. Also only a single TCP connection is associated with a host destination pair.

- **Additive Increase:** When total traffic is below capacity $R$, both connections add 1 MSS per RTT. On a graph comparing their speeds, this parallel growth moves their combined throughput at a 45-degree angle

- **Multiplicative Decrease:** When capacity $R$ is exceeded and packets drop, both connections cut their speeds exactly in half. They fall along a line passing through the origin.

- **The Result:** The connections zig-zag closer and closer to a perfect 50/50 split over time, regardless of which connection started with a larger window.

![[Screenshot 2026-09-12 at 1.42.26 AM.png]]

**Fairness Loopholes**

- **RTT Advantage:** AIMD operates strictly per Round Trip Time. A connection with a much shorter RTT cycles through its Additive Increase phase faster. This allows it to quickly grab available bandwidth and open its congestion window much faster than a connection suffering from high latency.

- **The UDP Bully:** UDP has no built-in congestion control. While TCP halves its rate during congestion, UDP applications (like live video streaming) continue blasting data at a constant rate, effectively crowding out the backing-off TCP traffic and hoarding the bandwidth.

- **Parallel Connection Cheating:** Network routers enforce fairness _per connection_, not per application or per user. If a bottleneck is currently shared by 9 existing connections, a new application opening 1 connection gets a fair 10% share ($R/10$). However, if that new application (like a web browser) intentionally opens 11 parallel TCP connections, it manipulates the mathematics of the router to seize over 50% of the total link capacity.

### QUIC (Quick UDP Internet Connections)

Developers at Google rolled their own protocol at the application layer. QUIC runs entirely on top of UDP to combine the speed of datagrams with the reliability of TCP, specifically designed to accelerate secure HTTP traffic (HTTP/3).

**Key Features of QUIC**

- **Fast, Secure Connection Establishment:** In traditional HTTP/1.1 or HTTP/2, a client must wait for a TCP 3-way handshake to complete before initiating a separate TLS handshake for encryption. QUIC collapses this process. It combines the connection state setup and the encryption authentication into a single handshake, drastically reducing the RTTs required to start sending data. All QUIC packets are natively encrypted.

- **Multiplexed Streams (Solving HOL Blocking):** QUIC introduces the concept of application-level "streams." Instead of shoving all web page assets (HTML, CSS, images) into a single sequential TCP pipeline, QUIC multiplexes them into separate streams within a single QUIC connection. If a UDP segment containing an image piece is dropped, only that specific stream pauses for retransmission. The text and CSS streams continue flowing without interruption.

- **Familiar Congestion Control:** Despite running over UDP, QUIC still requires congestion control to prevent network collapse. It borrows heavily from TCP, utilizing a congestion control algorithm based closely on TCP NewReno (an evolution of the Reno protocol you've been studying).

Because QUIC is implemented in the application layer (like inside the Chrome browser or YouTube app), developers can update its congestion control or connection mechanics continuously via standard software updates, without waiting for users to upgrade their operating systems.
